# От Vibe Coding к Spec Coding: Путь развития AI программирования

> "Code is a lossy projection of intent."
> Код — это неточное представление намерения.
> — Sean Grove, OpenAI, AI Engineer World's Fair 2025

## Основная идея Spec Coding: Все есть Markdown

Прежде чем углубляться в Spec Coding, поймите базовую философию Claude Code: **все есть Markdown**.

В философии дизайна Claude Code все процессы документации, передача информации, даже общение с моделью могут быть Markdown:

- **CLAUDE.md**: Markdown документ проектных стандартов
- **.claude/rules/**: Набор Markdown файлов многоуровневых стандартов
- **specs/**: Markdown описание требований функций
- **История беседы**: История беседы Claude Code сама по себе Markdown формат
- **AGENTS.md**: Markdown инструкции по поведению Agent

Это суть Spec Coding: **стандарт сам по себе это код**. Когда вы пишете требования, дизайн, критерии приема на Markdown, вы уже пишете «код» — AI прочитает этот Markdown, затем сгенерирует реальную реализацию кода.

Josh Beckman резюмировал выступление Grove очень точно:

> "Software engineering (and lawmaking and legal review) is specification repair."
> Программная инженерия (и разработка законов, и правовой анализ) по сути это исправление спецификаций.

В Claude Code этот процесс «исправления спецификаций» это: **Модифицировать Markdown → AI прочитает Markdown → Сгенерировать/Модифицировать код → Проверить результат**. Весь процесс управляется Markdown.

В 2025 году исследователь OpenAI **Sean Grove** представил выступление под названием **"The New Code"** на конференции AI Engineer World's Fair, что потрясло всё сообщество разработчиков. Это выступление способствовало рождению новой парадигмы разработки: **Spec Coding** (программирование по спецификации) — на спецификации, а не коде, как на основном продукте разработки, позволяя AI генерировать код согласно спецификации.

## 1. Выступление Sean Grove "The New Code": Разговор, меняющий мышление

В 2025 году исследователь OpenAI Sean Grove на конференции AI Engineer World's Fair представил выступление под названием **"The New Code"**. Это выступление широко считается истоком движения Spec Coding.

Grove ранее основал OneGraph (компания инструментов GraphQL разработки, позже куплена Netlify), сейчас работает в OpenAI над alignment reasoning — помощь в преобразовании высокоуровневого намерения в исполнимые спецификации и критерии оценки.

### 1.1 Основной тезис: код это неточное представление намерения

Основная концепция выступления Grove может быть кратко сформулирована в одном предложении:

> **Code is a lossy projection of intent.**
> Код это неточное представление намерения.

Что это означает? Когда вы переводите идею из головы в код, большой объем контекстной информации теряется — **почему** это нужно делать, **какие варианты были рассмотрены**, **какие ограничения учитывались**. Итоговый код содержит только «как это делать», но теряет «почему это так делать».

Это похоже на сжатие книги в один твит — объем информации резко снижается, оригинальное намерение серьезно искажается.

### 1.2 Суть программирования это общение

Grove выдвинул кажущееся простым но глубокое понимание:

> "If you can communicate effectively, you can program."
> Если вы можете эффективно общаться, вы можете программировать.

Он считает, что фактическая работа кодирования занимает только **10-20%** разработки, остальные 80% это вокруг требований и целей **структурированное общение** — понимание что хочет пользователь, согласование плана с командой, определение критериев приема, обработка граничных случаев.

Это означает что основное ядро способности к программированию — это **способность превращать неясные намерения в точные описания**.

### 1.3 Тот кто пишет спецификацию это программист

Это самая революционная точка зрения Grove:

> "Whoever writes the spec — be it a PM, a lawmaker, an engineer, a marketer — is now the programmer."
> Неважно PM, юрист, инженер или маркетер, кто пишет спецификацию — это программист.

С развитием AI в преобразовании спецификации в код, **реальная работа программирования** превращается из «написание кода» в «написание спецификации». Кто может наиболее точно выразить намерение, тот самый ценный «программист».

### 1.4 Спецификация имеет подобную коду инструментальную цепь

Grove указывает что спецификация может иметь подобную коду полную инструментальную цепь:

> "Specs actually give us a very similar toolchain, but it's targeted at intentions rather than syntax."

- **Комбинирование**: Спецификация может быть модульно скомбинирована, как модули кода
- **Тестирование**: Спецификация может встраивать модульные тесты, проверять соответствие поведения ожиданиям
- **Lint проверка**: Можно проверять размытый язык в спецификации, как Linter проверяет синтаксис кода
- **Проверка согласованности**: Спецификации разных отделов можно делать проверку согласованности, подобно проверке типов

### 1.5 OpenAI Model Spec: Живое доказательство

Grove использует собственный **Model Spec** документ OpenAI как доказательство.

Когда OpenAI обнаружила sycophancy (чрезмерное потакание пользователю) в модели, она не переучивала модель, а **модифицировала документ спецификации**. Изменение автоматически распространилось на всю систему, проблема была решена.

Это доказывает ключевой момент: **спецификация сама по себе может работать как «исполнимый код»**. Изменение спецификации равно изменению поведения, не нужно трогать ни одну строку традиционного кода.

Josh Beckman резюмировал выступление Grove очень точно:

> "Software engineering (and lawmaking and legal review) is specification repair."
> Программная инженерия (и разработка законов, и правовой анализ) это по сути исправление спецификации.

## 2. Spec Coding: Спецификация это код

### 2.1 Что такое Spec Coding

Spec Coding (программирование по спецификации), также называется Spec-Driven Development (SDD), это методология с **спецификацией как основным продуктом разработки**.

Основная идея: **сначала напишите спецификацию ясно, потом дайте AI сгенерировать код согласно спецификации. Спецификация это источник истины, код это только продукт реализации спецификации.**

Классический тезис Robert C. Martin в «Clean Code» возрождается в эпоху AI:

> "Specifying requirements so precisely that a machine can execute them is programming."
> Описание требований достаточно точно чтобы машина может выполнить это — это программирование.

### 2.2 Сравнение Vibe Coding и Spec Coding

| Измерение | Vibe Coding | Spec Coding |
|-----------|------------|-------------|
| **Способ** | Импровизированный prompt, итеративное уточнение | Сначала написать полную спецификацию, потом сгенерировать код |
| **Применимый сценарий** | Прототип, hackathon, исследование | Продакшн система, командное сотрудничество, корпоративное |
| **Качество кода** | Быстро но хрупко | Структурировано, тестируемо, проверяемо |
| **Первый проход успешно** | Нестабильно | Цель 95%+ |
| **Переиспользуемость** | Одноразовый prompt | Спецификация может переиспользоваться между проектами |
| **Безопасность** | Легко упустить | Встроено с уровня спецификации |
| **Документация** | Нет или отстает | Спецификация как документация, самодостаточно |
| **Командное сотрудничество** | Зависит от способностей к prompt отдельного лица | Разделяй спецификацию, единые стандарты |

Два способа не противоположны. Brad Jolicoeur указал:

> "Clever engineers will even use vibe coding as a first step to generate the initial draft of a specification."
> Умные инженеры даже используют Vibe Coding как первый шаг для генерирования начального черновика спецификации.

### 2.3 Трехуровневая структура спецификации Spec Coding

Инженер Red Hat обобщил практический трехуровневый модель спецификации:

**Первый уровень: Функциональная спецификация (What)**

Используйте естественный язык для описания ожидаемого результата, ответьте на «что делать»:

```markdown
## Функция аутентификации пользователя

### История пользователя
- Как новый пользователь, я хочу регистрироваться через электронную почту
- Как зарегистрированный пользователь, я хочу входить с электронной почтой и пароль
- Как пользователь который забыл пароль, я хочу сбросить пароль по электронной почте

### Критерии приема
- При регистрации проверить формат электронной почты и силу пароля
- После 5 ошибок входа, заблокировать аккаунт на 15 минут
- Ссылка сброса пароля действительна 30 минут
```

**Второй уровень: Спецификация независимая от языка (How - уровень архитектуры)**

Определить структуру данных, архитектурный паттерн, требования безопасности:

```markdown
## Технический дизайн

### Модель данных
- таблица users: id, email, password_hash, created_at, locked_until
- таблица sessions: id, user_id, token, expires_at

### Дизайн API
- POST /api/auth/register → 201 Created
- POST /api/auth/login → 200 OK + JWT
- POST /api/auth/reset-password → 202 Accepted

### Требования безопасности
- Пароль использовать bcrypt кодирование, cost factor ≥ 12
- JWT действительность 15 минут, refresh token 7 дней
- Все endpoints включить rate limiting
```

**Третий уровень: Спецификация специфичная для языка (How - уровень реализации)**

Требования версии, фреймворк тестирования, стандарты документации:

```markdown
## Ограничения реализации

### Технологический стек
- Runtime: Node.js 20+
- Framework: Express 5
- ORM: Prisma
- Testing: Vitest

### Правила кодирования
- Использовать TypeScript strict mode
- Обработка ошибок использовать кастомный класс AppError
- Все API endpoints нужны JSDoc комментарии
```

## 3. Практика Spec Coding в Claude Code

Теория понята, теперь смотри как применять в Claude Code. Дизайн философии Claude Code естественно совпадает с Spec Coding — его `CLAUDE.md`, Rules каталог, `/plan` команда, по сути это все про «управление через спецификацию».

OpenAI само также применяла похожий способ при построении проектов через Codex: используй `AGENTS.md` файл как спецификацию для управления AI agent. Их ключевой опыт — **когда agent встречает затруднение, считай это сигналом: найди что не хватает (инструмент, ограничение, документация), потом добавь в репозиторий**. Это точно совпадает с идеей Spec Coding: спецификация жива и нужна постоянно эволюционировать.

Исследование Augment Code также подтверждает это: **исполнимая спецификация остается точной потому что AI agent прямо генерирует код из спецификации, образуя принудительную функцию — устаревшая спецификация произведет плохую реализацию**. Это означает спецификация не будет как традиционная документация гнить.

### 3.1 Первый шаг: Используй CLAUDE.md для установки спецификации проекта

`CLAUDE.md` это живая спецификация вашего проекта. Каждый раз когда Claude Code запускается он прочитает это, как постоянное описание проекта для AI.

В предыдущей части [Claude Code быстрый старт основное руководство](https://github.com/datawhalechina/easy-vibe/blob/main/docs/zh-cn/stage-3/basics/index.md), мы выучили как создать `CLAUDE.md`. В контексте Spec Coding, его роль еще более важна — **это не просто конфигурационный файл, а вход в спецификацию проекта**.

Инженер LogRocket подчеркивает: **твердый контекст критичен для AI agent, это может предотвратить галлюцинации и неэффективность**. Без спецификации AI agent может сделать большие неконтролируемые изменения проекта. `CLAUDE.md` это первая линия защиты для предоставления этого «твердого контекста».

```markdown
# Спецификация электронного проекта

## Позиция проекта
SaaS платформа электронной торговли для микро бизнеса, поддержка мультимагазина, мультиканальных платежей.

## Решения по архитектуре
- Разделение фронтенда и бэкенда, API-first дизайн
- Микросервисная архитектура бэкенда, сервисы общаются через очередь сообщений
- Разделение чтения и записи базы данных

## Основные ограничения
- Все суммы используют целые числа (копейки) для хранения, избегайте проблем с точностью float
- Состояние заказа строго следует: ожидание оплаты → оплачено → отправлено → завершено
- Платежные интерфейсы должны быть идемпотентны
```

Инженер Aviator обобщил информацию которую спецификация должна захватить — это также то что вы должны покрыть при написании `CLAUDE.md`:

- Формат входа/выхода и тип данных
- Бизнес правила и граничные случаи
- Системные зависимости и ограничения
- Требования производительности и расширяемости
- Требования обработки ошибок и безопасности

### 3.2 Второй шаг: Используй Rules каталог для управления многоуровневыми спецификациями

Когда проект растет, один `CLAUDE.md` не достаточен. Это время использовать `.claude/rules/` каталог для организации многоуровневых спецификаций.

Это именно идея Augment Code про «исполнимую спецификацию»: **спецификация это не статический документ, а живые инструкции которые AI agent прямо использует**. Когда вы разделяете спецификацию на файлы Rules, каждый файл спецификации загружается только когда редактируются связанные файлы, это экономит токены и обеспечивает точность.

Инженер Tessl обнаружил что разделение требований на структурные документы — PRD определяет «делать что и почему», технические спецификации определяют «как делать» — может эффективно предотвратить AI «замешательство накопления» при долгой беседе, значительно улучшить согласованность выхода.

```
.claude/rules/
├── 00-architecture.md      # Спецификация архитектуры (глобально)
├── 01-security.md           # Спецификация безопасности (глобально)
├── 10-api-design.md         # Спецификация дизайна API
├── 11-frontend-patterns.md  # Спецификация фронтенд паттерна
├── 12-database.md           # Спецификация базы данных
└── 20-testing.md            # Спецификация тестирования
```

Каждый файл спецификации может через frontmatter указать применимый диапазон:

```markdown
---
globs:
  - "src/api/**/*.ts"
  - "src/services/**/*.ts"
---

# Спецификация дизайна API

## Дизайн маршрутов
- RESTful стиль, использовать множественное имя существительное: /api/v1/orders
- Вложенный ресурс максимум два уровня: /api/v1/users/123/orders

## Формат ответа
- Успех: { data, pagination? }
- Ошибка: { error: { code, message, details? } }

## Должен следовать
- Все операции записи требуют аутентификацию
- Интерфейсы списка должны поддерживать пагинацию
- Чувствительные операции записывают аудит логи
```

Таким образом, когда Claude Code редактирует связанные с API файлы, автоматически загружает эту спецификацию, обеспечивая что сгенерированный код соответствует стандартам.

### 3.3 Третий шаг: Используй /plan для реализации Specify → Plan → Tasks → Implement

Стандартный рабочий процесс Spec Coding это четырехэтапный цикл. GitHub Spec Kit стандартизировал его как Specify → Plan → Tasks → Implement, и `/plan` команда Claude Code естественно поддерживает этот процесс.

Группа SpecThis подчеркивает ключевой принцип: **определи границы перед запуском agent — узнай что должно изменяться перед изменением кода**. Это ценность `/plan`.

**Этап один: Specify (определить спецификацию)**

Сначала напишите ясно что делать, не спешите писать код:

```
/plan
Мне нужно реализовать функцию возврата заказа, спецификация как следует:

Требования функции:
- Пользователь может запросить полный возврат денег перед отправкой
- После отправки, можно запросить возврат товара в течение 7 дней
- Возврат требует одобрение администратора

Критерии приема:
- Сумма возврата не может превышать фактически оплаченную сумму заказа
- Состояние возврата: запрос → одобрено → возвращение → завершено
- После завершения возврата восстановить инвентарь
- Весь процесс записывается в журнал операций
```

**Этап два: Plan (технический план)**

Claude генерирует технический план на основе спецификации:

```
📋 План внедрения функции возврата

1. Дизайн модели данных
   - Создать таблицу refunds
   - Добавить состояния возврата в машину состояния заказа

2. Дизайн API
   - POST /api/orders/:id/refund - запросить возврат
   - PUT /api/refunds/:id/approve - одобрить возврат
   - GET /api/refunds - список возвратов

3. Бизнес логика
   - Проверка права на возврат
   - Расчет суммы возврата
   - Логика восстановления инвентаря

4. Интеграция
   - Интеграция с платежным каналом для возврата
   - Отправка уведомления о возврате
```

**Этап три: Tasks (разложение на задачи)**

Разложить план на независимо исполняемые маленькие задачи, каждая с четкими критериями завершения.

**Этап четыре: Implement (пошаговая реализация)**

Реализовать задачи по одной, после каждой задачи проверить.

### 3.4 Реальный пример: Использование Spec Coding для построения системы уведомлений пользователя

Давайте через полный пример противопоставить Vibe Coding и Spec Coding различия. Данные Orchestrator.dev показывают что в обследовании Stack Overflow 2025 84% разработчиков используют или планируют использовать AI инструменты, но только 22% удовлетворены результатом, 46% считают точность имеет проблемы. Spec Coding как раз решение для заполнения этого разрыва удовлетворения.

**Способ Vibe Coding:**

```
Вы: Сделайте функцию уведомлений
AI: [Напрямую начнет писать код, генерирует простой список уведомлений]

Вы: Нужна поддержка прочитанного/непрочитанного
AI: [Модифицирует код, добавляет поле read]

Вы: Нужна поддержка разных типов уведомлений
AI: [Снова модифицирует, добавляет поле type]

Вы: Нужна поддержка отправки на мобильный телефон
AI: [Большие изменения, предыдущая структура не очень подходит...]
```

Результат: изменения 4 раза, архитектура повторно переплетается несколько раз, код становится все более запутанным.

**Способ Spec Coding:**

Сначала напишите спецификацию документ `specs/notification.md`:

```markdown
# Спецификация системы уведомлений пользователя

## Требования функции
1. Поддержка три канала уведомления: внутренний, электронная почта, push уведомление
2. Типы уведомлений: системное объявление, состояние заказа, маркетинг, напоминание безопасности
3. Пользователи могут по каналам и типам настроить предпочтения уведомлений
4. Поддержка состояние прочитанное/непрочитанное, поддержка массовая отметка прочитанного

## Модель данных
- таблица notifications: id, user_id, type, channel, title, content,
  is_read, created_at
- таблица notification_preferences: user_id, type, channel, enabled

## Дизайн API
- GET /api/notifications?type=&is_read= - получить список уведомлений (пагинация)
- PUT /api/notifications/:id/read - отметить прочитанным
- PUT /api/notifications/read-all - отметить все прочитанными
- GET /api/notification-preferences - получить настройки предпочтений
- PUT /api/notification-preferences - обновить настройки предпочтений

## Критерии приема
- Число непрочитанных уведомлений обновляется в реальном времени
- Список уведомлений поддерживает бесконечную прокрутку
- Задержка push уведомления < 3 секунд
- Изменение предпочтений вступает в силу немедленно
```

Потом в Claude Code:

```
@specs/notification.md
По этой спецификации реализуйте систему уведомлений пользователя.
Начните с модели данных, потом API, наконец компонент фронтенда.
Каждый завершенный модуль делайте паузу, я его подтвержду перед продолжением.
```

Результат: одна разработка, архитектура ясна, не требует повторных переделок.

### 3.5 Усильте Spec Coding через Superpowers

В предыдущей части [Superpowers инженерная разработка](https://github.com/datawhalechina/easy-vibe/blob/main/docs/zh-cn/stage-3/core-skills/superpowers/index.md), мы выучили систему навыков Superpowers. Spec Coding и Superpowers это естественные партнеры:

| Этап Spec Coding | Соответствующий навык Superpowers |
|-------------------|-----------------------------------|
| Определить спецификацию | `brainstorming` — сократический способ уточнить требования |
| Технический план | `writing-plans` — разложение спецификации на маленькие задачи |
| Пошаговая реализация | `test-driven-development` — TDD красно-зеленая переработка |
| Проверка качества | `code-review` + `verification-before-completion` |

**Пример комбинированного использования:**

```
@specs/notification.md
Используй TDD способ по этой спецификации реализовать систему уведомлений,
после завершения помогите мне сделать проверку кода
```

Эта команда одновременно запускает рабочий процесс Spec Coding и навыки TDD + Code Review из Superpowers, образуя полный процесс инженерной разработки.

### 3.6 Контроль версии спецификации и постоянная эволюция

The Vibe Coding Substack выдвинул важную точку зрения: **Спецификация это теперь код**. Раз спецификация это код, должна управляться как код:

- **Контроль версии**: Файлы спецификации поместить в Git репозиторий, коммитить вместе с кодом
- **Отслеживание изменений**: Каждое изменение спецификации имеет запись коммита, знайте кто что изменил и почему
- **Code Review**: Изменения спецификации тоже требуют PR проверку, обеспечьте согласование команды
- **CI интеграция**: Изменения спецификации запускают автоматизированные тесты, проверьте что реализация все еще соответствует спецификации

В Claude Code это означает вашу `CLAUDE.md`, `.claude/rules/` и `specs/` каталог все должны быть в контроле версии. Опыт Robomotion: **спецификация и реализация версионированы вместе, предотвращают дрейф, сохраняют проверяемость**.

OpenAI практика Harness Engineering тоже подтверждает это: их файл `AGENTS.md` сам был написан Codex, и постоянно обновляется с эволюцией проекта. Когда agent встречает затруднение, решение не изменить код, а **позволить самому Codex обновить спецификацию** — образуя цикл самоисправления спецификации.

## 4. Гибридная стратегия: Пошаговая переход от Vibe к Spec

Консенсус индустрии не «отказаться от Vibe Coding», а **выбрать подходящий способ в зависимости от сценария**.

### 4.1 Когда использовать Vibe Coding

- Проверка возможности идеи (прототип за 30 минут)
- Исследование незнакомой технологии или фреймворка
- Hackathon или внутренний demo
- Одноразовый скрипт или инструмент

### 4.2 Когда использовать Spec Coding

- Разработка функции продакшн уровня
- Многолюдные сотрудничества проектов
- Требуемо долгосрочное обслуживание кода
- Затрагивают безопасность, платежи, данные и другие чувствительные области
- Дизайн API и системная интеграция

### 4.3 Рекомендуемый пошаговый рабочий процесс

**Этап один: Vibe исследование**

Используй Vibe Coding для быстрой проверки идеи, не писать спецификацию, не беспокоиться о качестве кода:

```
Сделайте простое уведомление всплывающего окна, посмотрите эффект
```

**Этап два: Извлечение спецификации**

После проверки возможности, извлеките открытия исследования в спецификацию. Вы даже можете попросить AI помочь:

```
На основе уведомления всплывающего окна прототипа который мы только что сделали,
помогите мне организовать формальный документ спецификации функции,
включить модель данных, дизайн API и критерии приема
```

**Этап три: Spec восстановление**

На основе спецификации, используй Spec Coding способ заново реализовать продакшн версию:

```
@specs/notification.md
По этой спецификации с нуля реализуйте, не рассмотрите предыдущий код прототипа
```

Преимущество этого процесса: **используй скорость Vibe Coding для проверки направления, используй качество Spec Coding для доставки продукта**.

Обобщение Robomotion очень уместно:

> "The spec is the source of truth. The AI generated output is the draft implementation. Validation is not optional."
> Спецификация это единственный источник истины. Генерированный AI выход это черновик реализации. Проверка не опционна.

## 5. Часто задаваемые вопросы

### Q1: Не медленно ли Spec Coding?

Написание спецификации точно требует фронтальных инвестиций. Но команда Greg Ceccarelli используя Spec Coding способ, **3 человека за 4 недели доставили полный macOS продукт** — это в традиционной разработке почти невозможно.

Время, потраченное на написание спецификации впереди, будет возмещено сокращением возделки, сокращением багов, сокращением стоимости общения позже.

### Q2: Насколько детально писать спецификацию?

Рекомендация Robomotion: **высококачественная спецификация может быть только одна страница**. Ключ ответить 8 вопросов:

1. Что мы автоматизируем?
2. Что входит?
3. Что выходит?
4. Какие ограничения?
5. Какие режимы отказа?
6. Какие требования безопасности?
7. Какие требования производительности?
8. Какой тест доказывает это работает?

### Q3: AI делает ровно что написано в спецификации, что если забыл «очевидное» функционирование?

Это действительно ограничение Spec Coding. Обратная связь пользователей GitHub Spec Kit: AI будет "exactly and only" делать написанное в спецификации.

Решение: добавьте раздел «нефункциональные требования» в спецификацию, перечислите универсальные ожидания (обработка ошибок, логирование, доступность и т.д.). Или установите глобальные правила в `CLAUDE.md`.

### Q4: Маленький проект тоже требует Spec Coding?

Не требует. Spec Coding подходит:
- Продакшн проекты
- Многолюдные сотрудничества проекты
- Требуемо долгосрочное обслуживание

Для быстрого прототипа, одноразового скрипта, учебного эксперимента, Vibe Coding более подходит.

### Q5: Как сделать команду принять Spec Coding?

Начните с одной маленькой функции как пилотное испытание. Позвольте команде видеть что Spec Coding снижает возделку, улучшает первый проход успешно эффект. Обследование Stack Overflow 2025 показывает 84% разработчиков используют или планируют использовать AI инструменты, но только 22% удовлетворены результатом — Spec Coding точно это ключ улучшения удовлетворения.

## 6. Резюме

От Vibe Coding к Spec Coding, не революция, а эволюция.

Sean Grove в «The New Code» очень ясно сказал: **70 лет мы писали код для решения проблем, сейчас должны писать спецификацию для генерирования кода**. Код это неточное представление намерения, только спецификация может полностью захватить намерение, контекст и ограничения.

Для разработчиков которые использую Claude Code, это преобразование уже происходит:

- Ваш написанный `CLAUDE.md` это спецификация проекта
- Ваш настроенный Rules каталог это многоуровневая спецификация
- Ваш использованный `/plan` это процесс Specify → Plan → Tasks
- Ваш комбинированный Superpowers TDD и Code Review это полный процесс Spec Coding

**Ключевые моменты:**

- Vibe Coding подходит исследованию и прототипу, Spec Coding подходит продакшну и сотрудничеству
- Спецификация это источник истины, код это продукт реализации спецификации
- Способность писать спецификацию = способность программировать, способность общения > способность синтаксиса
- Начните с малого: хорошо напишите `CLAUDE.md`, уже сделали первый шаг в Spec Coding

> 💡 Следующий шаг
> В следующей главе мы научимся использовать Agent Teams функцию Claude Code, позволяя несколько AI экземплярам работать вместе как реальная команда разработки.
