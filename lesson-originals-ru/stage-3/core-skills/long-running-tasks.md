# Как позволить Claude Code длительное время работать

## Введение

Вы, вероятно, уже использовали базовый API Claude — отправляете сообщение, получаете ответ, готово. Но если вы хотите, чтобы Claude помог вам переделать целый проект, но он пишет несколько файлов и говорит "готово"; или вы хотите, чтобы Claude постоянно исправлял баги, пока все тесты не пройдут, но он запускает их один раз и останавливается; или вы хотите, чтобы Claude "работал всю ночь", но утром обнаруживаете, что он остановился давно — для всех этих сценариев базовый API недостаточен.

Летом 2025 года австралийский разработчик по имени Geoffrey Huntley (кстати, он пастух) написал простой bash-скрипт из 5 строк. Этот скрипт просто постоянно перезапускал Claude Code и давал ему одну и ту же задачу. Он назвал его "Ralph Wiggum" — в честь персонажа из "Симпсонов", который постоянно пытается и никогда не сдаётся.

Этот простой скрипт поразил весь Кремниевую долину. За две недели связанный проект получил 7000+ звёзд на GitHub. За одну ночь люди сгенерировали 6 полных проектов, потратив всего $297 на API вместо $50 000 стоимости работы. Даже были случаи, когда за 3 месяца люди построили целый язык программирования.

Суть этого раздела в следующем: как позволить Claude Code работать, как настоящему разработчику, непрерывно, пока задача действительно не будет завершена.

## Основной принцип: почему AI "преждевременно останавливается"?

Прежде чем обсуждать различные методы, давайте разберёмся с корнем проблемы.

### AI не может надёжно оценить собственное выполнение

LLM (большие языковые модели) имеют фундаментальный дефект: они не могут точно判断 собственную работу действительно завершена или нет.

Критерии завершения для человека объективны — все тесты пройдены, функциональность работает полностью, качество кода в норме. Но AI может судить только по "ощущениям". Оно может подумать "кажется, готово" и остановиться; или "я вывел достаточно" и прекратить; или "я не знаю, что дальше" и остановиться.

Вот почему нам нужна внешняя система, которая判断, действительно ли задача завершена, вместо того чтобы полагаться на собственную оценку AI.

### Основная идея решения

Ядро решения в том, чтобы позволить AI работать в "цикле".

Каждый раз, когда оно хочет выйти, внешняя система задаёт три вопроса — правда ли завершено? Соответствует ли объективным критериям? Ничего не упущено? Если нет, система переиспользует задачу и начинает следующий цикл.

Эту идею можно реализовать по-разному, от простого bash-скрипта до сложной системы оркестровки, но суть одна.

## Способ первый: While True Bash Loop (самый примитивный способ)

Это самый простой и прямолинейный способ реализации. По сути, это бесконечный цикл, в котором каждая итерация перезапускает Claude Code и даёт ему одну и ту же описание задачи.

Самая простая реализация занимает всего 5 строк кода:

```bash
#!/bin/bash
while true; do
    cat PROMPT.md | claude
done
```

### Как это работает

Рабочий процесс скрипта очень прямолинеен. Первый шаг — прочитать описание задачи из файла PROMPT.md. Второй шаг — запустить Claude Code и передать ему описание задачи. Третий шаг — Claude начинает работать и выводит результаты. Четвёртый шаг — Claude завершает работу и выходит. Пятый шаг — цикл автоматически перезапускается и весь процесс повторяется, образуя бесконечный цикл — до тех пор, пока вы не нажмёте Ctrl+C и не прерветесь.

### Плюсы и минусы

Преимущество этого метода в его экстремальной простоте — любой может разобраться, не требует конфигурации, можно использовать сразу, подходит для быстрых экспериментов.

Но недостатки очевидны: он не может判断, действительно ли задача завершена, может крутиться бесконечно впустую, нет механизмов безопасности, будет тратить вызовы API.

### Пример использования в реальности

Сначала создайте файл PROMPT.md с описанием задачи. Например, задачу переделать модуль аутентификации можно написать так:

```markdown
# Задача: переделать модуль аутентификации пользователей

Требования:
1. Извлечь всю логику аутентификации в отдельный класс AuthService
2. Добавить модульные тесты с покрытием > 80%
3. Обновить соответствующую документацию

Когда все тесты пройдут и документация обновится, выведите: готово
```

Затем создайте скрипт цикла и запустите его:

```bash
chmod +x loop.sh
./loop.sh
```

### Версия с улучшениями безопасности

Чтобы избежать бесконечного цикла, можно добавить ограничение на количество итераций:

```bash
#!/bin/bash
MAX_ITERATIONS=50
iteration=0

while true; do
    iteration=$((iteration + 1))
    echo "=== Итерация $iteration/$MAX_ITERATIONS ==="

    cat PROMPT.md | claude

    if [ $iteration -ge $MAX_ITERATIONS ]; then
        echo "Достигнуто максимальное количество итераций, остановка"
        break
    fi

    sleep 5  # Небольшая пауза, чтобы избежать ограничения скорости API
done
```

Эта улучшенная версия добавляет ограничение на максимальное количество итераций, отображает текущий прогресс на каждой итерации и останавливается при достижении лимита. Также добавляется 5-секундная пауза между циклами, чтобы избежать срабатывания ограничения скорости API.

## Способ второй: Ralph Wiggum Plugin (официально рекомендуемый)

Ralph Wiggum — это официальный плагин от Anthropic, специально предназначенный для решения проблемы длительных задач. Его назвали в честь персонажа из "Симпсонов", символизирующего спирит "несмотря на провалы, продолжай пытаться".

### Основной механизм: Stop Hook

Основной механизм Ralph — это Stop Hook. Когда Claude хочет выйти, Stop Hook перехватывает этот сигнал выхода. Затем система проверяет: был ли выведен определённый маркер завершения? Если маркер не найден, система переиспользует исходный prompt и начинает следующий раунд итераций. Если маркер найден, Claude позволяется выйти.

Этот механизм гарантирует, что Claude не остановится только потому что "кажется готово", а должен действительно завершить чётко обозначенную задачу.

### Установка

Ralph Wiggum — это официальный плагин Claude Code, есть два способа установки.

**Способ 1: установка через официальный магазин плагинов (рекомендуется)**

```bash
# Запустите Claude Code
claude

# Добавьте официальный магазин плагинов
/plugin marketplace add anthropics/claude-code

# Установите Ralph Wiggum
/plugin install ralph-wiggum@claude-code-plugins

# Проверьте установку
/plugin
```

**Способ 2: прямая установка с GitHub**

```bash
# Перейдите в директорию плагинов
cd ~/.claude/plugins/

# Клонируйте репозиторий плагина
git clone https://github.com/anthropics/ralph-wiggum-plugin.git
```

После установки вы можете использовать следующие команды:

- `/ralph-wiggum:ralph-loop` — запустить цикл
- `/ralph-wiggum:cancel-ralph` — отменить цикл
- `/ralph-wiggum:help` — показать справку

### Базовое использование

Базовый способ использования — через команду `/ralph-wiggum:ralph-loop`:

```bash
/ralph-wiggum:ralph-loop "Построить API待办列表 с CRUD операциями, валидацией ввода, тестами.
             Когда всё будет готово, выведите <promise>COMPLETE</promise>" \
  --max-iterations 50 \
  --completion-promise "COMPLETE"
```

### Описание параметров

Два самых важных параметра — это `--max-iterations` и `--completion-promise`.

`--max-iterations` устанавливает максимальное количество итераций, это механизм безопасности, рекомендуемое значение между 20-100. Даже если задача не завершена, после достижения этого количества цикл остановится, предотвращая неограниченное потребление API-квоты.

`--completion-promise` указывает текст маркера завершения, это должен быть определённый уникальный идентификатор. Когда выход Claude содержит этот маркер, Ralph считает задачу завершённой и позволяет выйти. Рекомендуется использовать чёткие маркеры вроде `COMPLETE`, `TASK_DONE`, избегайте неясных слов.

### Лучшие практики написания Prompt

Написание хорошего Prompt — ключ к успеху Ralph.

Плохой Prompt обычно не имеет чётких критериев завершения. Например, просто сказать "напишите API待办列表", тогда AI может написать базовый фреймворк и считать готово, без тестов, без валидации, без документации.

Хороший Prompt должен содержать детальные поэтапные требования и чёткие критерии приёма. Например, можно написать так:

Сначала опишите задачу по этапам. Этап 1 — базовая функциональность, перечислите все CRUD эндпоинты: POST /todos создание задачи, GET /todos получение списка, GET /todos/:id получение одной, PUT /todos/:id обновление, DELETE /todos/:id удаление. Этап 2 — валидация ввода, название не может быть пусто, статус завершения должен быть булевым. Этап 3 — тестирование, напишите тесты для каждого эндпоинта с покрытием больше 80%.

Затем перечислите критерии приёма: все тесты пройдены, код прошёл проверку linter, README содержит документацию API.

Наконец укажите уникальный маркер завершения: `<promise>TODO_API_COMPLETE</promise>`.

Таким образом Claude знает точно что делать и когда это действительно будет завершено.

### Дополнительные примеры шаблонов Prompt

Вот несколько шаблонов Prompt для общих задач, вы можете использовать их напрямую или модифицировать по необходимости.

**Шаблон 1: миграция тестов (Jest → Vitest)**

```
/ralph-wiggum:ralph-loop "
Мигрируйте все тесты в проекте с Jest на Vitest:
- Сохраните всю логику тестов
- Обновите файлы конфигурации (vite.config.js, vitest.config.js)
- Замените API специфичные для Jest (например jest.mock → vi.mock)
- Убедитесь что все тесты проходят
- Удалите зависимости Jest

Критерии приёма:
- npm test полностью проходит
- В package.json нет зависимостей jest
- Проект нормально собирается

Выведите по завершении: <promise>VITEST_MIGRATION_COMPLETE</promise>
" --max-iterations 40 --completion-promise "VITEST_MIGRATION_COMPLETE"
```

**Шаблон 2: оптимизация UI/UX (приоритет мобилы)**

```
/ralph-wiggum:ralph-loop "
Сделайте UI/UX этого проекта более похожим на отполированное приложение для изучения языков с приоритетом на мобильные устройства:
- Единообразное расстояние и отступы (используйте 4px как базовую единицу)
- Установите чёткую иерархию шрифтов (заголовки/основной текст/вспомогательная информация)
- Единообразный стиль карточек, списков и других компонентов
- Добавьте нижнюю навигацию (Домой/Учиться/Викторина/Прогресс/Настройки)
- Убедитесь хороший вид на мобильных устройствах

Критерии приёма:
- npm run build успешно выполняется
- Нет ошибок TypeScript
- Основные страницы хорошо выглядят на мобильном экране

Выведите по завершении: <promise>UI_UX_COMPLETE</promise>
" --max-iterations 25 --completion-promise "UI_UX_COMPLETE"
```

**Шаблон 3: массовое добавление типов TypeScript**

```
/ralph-wiggum:ralph-loop "
Добавьте аннотации типов TypeScript для всех функций в проекте:
- Приоритет на директорию src/
- Добавьте типы для параметров функций и возвращаемых значений
- Избегайте использования any, используйте конкретные типы или unknown
- Добавьте необходимые определения типов

Критерии приёма:
- npm run typecheck проходит
- Нет комментариев @ts-ignore или @ts-any
- Код нормально работает

Выведите по завершении: <promise>TYPES_ADDED</promise>
" --max-iterations 30 --completion-promise "TYPES_ADDED"
```

**Шаблон 4: разработка через TDD**

```
/ralph-wiggum:ralph-loop "
Реализуйте функцию оформления заказа через TDD:
1. Сначала напишите тесты (checkout.test.ts)
2. Запустите тесты (они будут падать)
3. Напишите минимальный код чтобы тесты прошли
4. Рефакторьте и оптимизируйте
5. Повторяйте пока все тесты не пройдут

Требования функциональности:
- Список товаров в корзине
- Расчёт доставки
- Применение купонов скидок
- Валидация формы платежа

Критерии приёма:
- Все тесты проходят (npm test checkout.test.ts)
- Покрытие кода > 80%
- Нет ошибок ESLint

Выведите по завершении: <promise>CHECKOUT_COMPLETE</promise>
" --max-iterations 25 --completion-promise "CHECKOUT_COMPLETE"
```

**Шаблон 5: унификация стиля кода**

```
/ralph-wiggum:ralph-loop "
Унифицируйте стиль кода в проекте:
- Форматируйте все файлы через Prettier
- Унифицируйте соглашение об имённах (переменные camelCase, компоненты PascalCase)
- Удалите неиспользуемые импорты и переменные
- Унифицируйте кавычки для строк (одинарные)
- Унифицируйте использование точек с запятой (не использовать)

Критерии приёма:
- npm run lint проходит
- Стиль кода единообразен
- Сборка успешна

Выведите по завершении: <promise>STYLE_UNIFIED</promise>
" --max-iterations 20 --completion-promise "STYLE_UNIFIED"
```

Установили максимум 200 итераций и пошли спать.

На следующее утро они обнаружили 6 демонстрируемых проектов, при этом затратив на API всего 297 долларов. Вот это сила Ralph — пока ты спишь, AI работает.

Другой пример от Boris Cherny (руководителя Claude Code). Он использовал Ralph с моделью Opus 4.5 и за 30 дней создал 259 PR с 497 коммитами, добавив 40 000 строк кода и удалив 38 000. Самое поразительное — это 100% было сделано Claude Code без участия человека, человек не писал ни одной строки кода.

Ещё более сумасшедший пример: язык программирования CURSED. Это язык, созданный Geoffrey Huntley (автор Ralph) с помощью Ralph Loop за 3 месяца самостоятельно. Особенность этого языка в том, что он использует Gen Z сленг как ключевые слова (например `slay`, `sus`, `based`), но что более важно, он включает полную реализацию LLVM компилятора, стандартную библиотеку и частичную поддержку редактора. Этот проект показывает настоящий потенциал Ralph Loop — дайте ему чёткую цель, и оно будет работать несколько месяцев, пока не завершит сложный проект до конца.

### Ещё больше реальных примеров

**Автоматический рефакторинг проекта**

Один разработчик использовал Ralph для рефакторинга наследственного проекта. Проект был беспорядочным, без тестов, документация отсутствовала. Он дал Ralph задачу:

1. Добавить тесты к существующему коду
2. Постепенно рефакторить, убедиться что тесты проходят после каждого рефакторинга
3. Обновить документацию

Запустил Ralph на целый выходной. В понедельник обнаружил что проект совершил 47 коммитов, структура кода чистая, покрытие тестами 75%, есть полная документация API. Затраты около 12 долларов.

### Философия Ralph

Ralph воплощает три основные философские принципа.

Первое — итерация лучше совершенства. Не ожидайте идеального с первого раза, позвольте циклу улучшаться. Первый раз может быть только фреймворк, второй раз исправятся баги, третий раз оптимизируется код, четвёртый раз добавляются тесты, каждый раз лучше чем предыдущий.

Второе — провал это данные. Каждый провал теста это возможность улучшения, не бойтесь провалов, учитесь на них.

Третье — непрерывная попытка. Keep trying until it works — вот дух Ralph.

### Когда подходит/не подходит использовать Ralph

Важно понимать сценарии применения Ralph, это поможет вам сэкономить время и деньги.

**✅ Сценарии, где подходит Ralph**

Эти задачи имеют чёткие критерии завершения, подходят для автоматизированной итерации Ralph:

| Сценарий | Причина |
|------|------|
| Миграция тестов | Есть чёткая цель (новый фреймворк), прохождение тестов подтверждает успех |
| Большой рефакторинг | Можно определить конкретные правила рефакторинга |
| Миграция фреймворка | Код работает нормально после миграции |
| Массовое добавление типов | typecheck проходит = готово |
| Повышение покрытия тестами | Процент покрытия это объективный метрик |
| Генерация документации | Документацию API можно автоматически проверить |
| Унификация UI/UX | Можно определить конкретные правила дизайна |
| Исправление баги (есть шаги воспроизведения) | Тесты проходят = баг исправлен |

**❌ Сценарии, где не подходит Ralph**

Эти задачи требуют человеческого суждения или исследования, не подходят для Ralph:

| Сценарий | Причина |
|------|------|
| Решения по архитектуре | Микросервисы vs монолит нужно взвешивать |
| Код связанный с безопасностью | Уязвимости могут быть скрыты |
| Задачи с неясными требованиями | Нет чётких критериев завершения |
| Исследовательская работа | Нужно постоянно менять направление |
| Творческий дизайн | Нужно человеческое эстетическое суждение |
| Простая разовая задача | Использовать Ralph это пустая трата |

**💡 Критерии решения**

Задайте себе три вопроса:
1. **Я могу определить чёткие критерии завершения?** Если нет, не подходит
2. **Есть ли объективный способ проверки?** (тесты, сборка, проверка типов) Если нет, не подходит
3. **Эта задача требует моего постоянного обратного связа?** Если да, не подходит

Если три ответа "нет", тогда смело позволяйте Ralph это делать!

## Способ третий: расширенный Ralph

Это расширенная реализация Ralph от сообщества, найти можно на GitHub проект [frankbria/ralph-claude-code](https://github.com/frankbria/ralph-claude-code), добавляет больше механизмов безопасности.

### Дополнительные возможности

Расширенная версия предоставляет несколько дополнительных механизмов безопасности.

Первый — двойной критерий выхода. Официальный Ralph нужно только проверить маркер завершения, но расширенная версия требует одновременного выполнения маркера завершения и явного EXIT_SIGNAL чтобы действительно остановиться. Это значит что даже если Claude вывел маркер завершения, если оно не явно выразило готовность выхода, цикл продолжится, позволяя дополнительную проверку и улучшение.

Второй — функция ограничения скорости. Стоит по умолчанию 100 раз/час, предотвращает ситуацию когда из-за какого-то бага происходит неконтролируемый цикл и счёт за API взлетает. Вы можете отрегулировать это ограничение по необходимости.

Третий — умный выключатель цепи. Если система постоянно на протяжении 5 раз обнаруживает маркер завершения, принудительно выходит. Это защита от редкого граничного случая, когда цикл не может нормально завершиться.

Четвёртый — живая приборная панель. Расширенная версия предоставляет интерфейс командной строки, может отображать текущее количество итераций, прогресс задачи, предполагаемые затраты и другую информацию, позволяя вам всегда знать состояние.

### Установка

Установка расширенного Ralph требует сначала клонировать репозиторий с GitHub:

```bash
git clone https://github.com/frankbria/ralph-claude-code.git
cd ralph-claude-code
./install.sh
```

Скрипт установки автоматически настроит необходимые файлы и конфигурацию.

### Использование

Использование расширенного Ralph состоит из двух шагов. Сначала используйте команду `ralph-setup` для инициализации проекта:

```bash
ralph-setup my-project
```

Это создаст необходимые файлы конфигурации в проекте. Затем используйте команду `ralph loop` для запуска цикла:

```bash
ralph loop
```

### Файл конфигурации

Расширенный Ralph использует файл конфигурации `.claude/ralph-config.json` для настройки параметров:

```json
{
  "maxIterations": 50,
  "rateLimitPerHour": 100,
  "completionPromise": "TASK_COMPLETE",
  "exitSignal": "EXIT_NOW",
  "costAlertThresholds": [10, 50, 100]
}
```

`maxIterations` это максимальное количество итераций. `rateLimitPerHour` это ограничение скорости за час. `completionPromise` это текст маркера завершения. `exitSignal` это сигнал явного выхода. `costAlertThresholds` это пороги предупреждения стоимости, когда затраты достигнут этих сумм будут выданы предупреждения.

## Способ пятый: фоновые задачи (Ctrl+B)

Это простой но практичный метод неблокирующего выполнения.

### Базовые операции

Способ использования очень интуитивен. Когда Claude начинает выполнять задачу, вы можете нажать `Ctrl+B` чтобы отправить её в фоновый режим.

Например вы говорите "запустить полный набор тестов". Claude начинает запускать. Вы можете нажать `Ctrl+B`, Claude вернёт "Задача отправлена в фон (ID: task_abc123)". Затем вы можете сказать "одновременно помоги мне проанализировать этот файл лога". Claude будет анализировать лог пока тесты работают в фоне.

### Просмотр фоновых задач

Есть несколько способов просмотра фоновых задач. Используйте команду `/tasks` чтобы вывести список всех фоновых задач, включая ID задачи, статус, время запуска и другую информацию. Нажмите `Ctrl+T` чтобы быстро просмотреть краткую информацию о статусе задач. Вы также можете выбрать задачу из списка, вернуть её в передний план (Bring to foreground) и посмотреть её реальный вывод.

### Применимые сценарии

Фоновые задачи подходят для нескольких типичных сценариев.

Первый — долгих запусков тестов. Полный набор тестов может занять десятки минут, с фоновыми задачами вы можете продолжить разработку пока тесты работают.

Второй — сборка больших проектов. Процесс сборки может занять много времени, фоновый запуск не блокирует другую работу.

Третий — обработка файлов в пакетах. Например массовое переименование, массовое форматирование, можно делать в фоне.

Четвёртый — всё что вы не хотите ждать.

## Механизмы безопасности: предотвращение бесконечных циклов

Любая система автоматического цикла должна иметь защиту, иначе может произойти выход из-под контроля.

### Жёсткие лимиты

Самая базовая защита — установить `--max-iterations` (максимальное количество итераций), это обязательно. Независимо от того завершена ли задача, после достижения этого количества остановится, предотвращая неограниченное потребление API-квоты.

Вы также можете установить временное ограничение, например максимум 4 часов работы и автоматическая остановка. Или установить предупреждение по бюджету API, когда затраты достигнут определённой суммы (например 10, 50, 100 долларов) пауза и уведомление.

### Умная обнаружение

Можно добавить умную обнаружение для выявления мёртвых циклов. Например проверить есть ли реальные изменения в последних нескольких коммитах:

```bash
if [ $(git diff HEAD~5 | wc -l) -eq 0 ]; then
    echo "Последние 5 коммитов не имеют реальных изменений, возможен цикл"
    exit 1
fi
```

Если различия в коде между последними 5 коммитами очень малы, это значит возможен мёртвый цикл, нужно остановиться и дать сигнал.

### Предупреждение по стоимости

В файле конфигурации можно установить пороги предупреждения стоимости:

```json
{
  "costAlertThresholds": [10, 50, 100],
  "alertAction": "pause_and_notify"
}
```

Когда затраты достигнут 10, 50, 100 долларов, система пауза и отправит уведомление, позволяя вам решить продолжать ли дальше.

### Контрольные точки с участием человека

Для особо важных задач можно установить контрольные точки человека:

```bash
if [ $((iteration % 10)) -eq 0 ]; then
    read -p "Завершено $iteration итераций, продолжить? (y/n)" answer
    if [ "$answer" != "y" ]; then
        break
    fi
fi
```

Таким образом каждые 10 итераций пауза и ожидание вашего подтверждения. Это позволяет немедленно вмешаться если возникает проблема.

**Четвёртая, финальная проверка нужна вручную**. AI может пропустить граничные случаи или специальные сценарии, особенно для функций связанных с безопасностью.

**Пятая, дизайн БД нужно тщательно**. Ralph может потребоваться несколько итераций чтобы спроектировать разумную структуру базы данных.

## Сравнение методов и выбор

Различные методы имеют свои особенности, подходят для разных сценариев.

While True Loop это простейший, только 5 строк кода и работает, подходит для быстрых экспериментов и проверки прототипа. Но функционал ограничен, нет обнаружения завершения, можно только полагаться на ограничение итераций.

Ralph Wiggum это универсальная рекомендация, подходит для большинства сценариев. Имеет полный механизм Stop Hook, поддерживает обнаружение маркеров завершения, имеет официальную поддержку, документация полная.

Расширенный Ralph больше подходит для производственных окружений, имеет двойной критерий выхода, ограничение скорости, умные выключатели цепи и другие дополнительные механизмы безопасности.

Фоновые задачи подходят для простого неблокирующего выполнения, только нужно нажать `Ctrl+B`. Но это только простой фоновый запуск, нет механизма цикла.

## Итоги

Основная идея позволить Claude Code длительное время работать очень простая: не давайте ему задачу "завершить один раз", а позвольте ему "непрерывно пытаться пока действительно не завершит".

Все методы по сути делают одно и то же: дайте Claude задачу, позвольте ему работать, проверьте действительно ли завершено, если нет, продолжите следующий раунд.

Выбор метода зависит от ваших конкретных требований.

Если нужна простота и скорость, используйте While True Loop. 5 строк кода работают, но функционал ограничен.

Если нужна универсальная рекомендация, используйте Ralph Wiggum. Официальная поддержка, полный функционал, подходит для большинства сценариев.

Если это производство, используйте расширенный Ralph. Имеет дополнительные механизмы безопасности, более надёжен.

(Содержание многоагентского сотрудничества Agent Teams см. в следующем разделе "3.3 Agent Teams многоагентское сотрудничество")

Надеемся что содержание этого раздела поможет вам лучше использовать Claude Code, позволяя AI действительно стать инструментом производительности, а не только чатботом.
