# Dify — введение и интеграция базы знаний

# Повтор предыдущего урока

В предыдущих уроках мы разделенно изучали основы AI-программирования, инженерии подсказок (prompt engineering) и создания изображений с помощью AI. Эти знания помогли нам понять граница и возможности различных больших языковых моделей (LLM, Large Language Model) и генеративных моделей.

Чтобы помочь вам повторить материал предыдущего урока, ниже приведены несколько вопросов для размышления:

1. Что такое AI-программирование? Как использовать инструменты AI-программирования (например, [z.ai](http://z.ai)) для создания веб-страницы?
2. Что такое большая языковая модель? Что такое инженерия подсказок и инженерия контекста? Как написать сложную подсказку?
3. В трех направлениях — текст, AI Coding, генерация изображений — как вы думаете, где проявляются сильные и слабые стороны возможностей модели в каждом случае?

Если у вас остаются вопросы по какому-либо из них, вы можете пересмотреть документы предыдущего урока или напрямую задать вопросы в чат-группе WeChat.

В этом уроке мы перейдем от простых инструментов создания текста и изображений с помощью AI к платформам построения рабочих процессов, которые ближе к реальному внедрению в бизнес. От чат-ботов мы перейдем к AI-агентам, AI-рабочим процессам и сделаем их интерактивными "умными" ботами на странице путем интеграции с API.

Если во время операций вы столкнетесь с непонятными шагами, не волнуйтесь. Рекомендуется сделать скриншот текущей страницы операции и отправить его большой языковой модели для уточнения. Современные большие модели уже могут ответить на большинство типичных вопросов.

Если проблема остается нерешенной после запроса, не бойтесь попробовать операцию самостоятельно. Ошибки — это возможности для обучения и прогресса. С увеличением количества попыток вы станете все более опытными и уверенными!

# 1. От диалога к агентам

На предыдущем этапе мы научились использовать подсказки для того, чтобы большие модели исполняли роли, генерировали текст или писали простой код. Однако, если вы внимательно подумаете, обнаружите проблему: сам чат-бот не может выполнять действия.

Он может ответить на вопрос "Как проверить мой заказ?", но не может действительно заглянуть в базу данных и найти соответствующие числа. Он может описать, что должна содержать еженедельная справка, но не может автоматически собрать данные вашего проекта и отправить письмо. Это ограничение "говорить, но не делать" затрудняет интеграцию чистого диалогового AI в бизнес-процессы.

Чтобы поднять AI от компаньона для разговора к цифровому работнику, нам нужно дать ему три ключевых навыка:

1. Собственные знания — позволить ему полностью прочитать и понять вашу документацию продукта, информацию о клиентах, внутренние политики;
2. Вызов инструментов (или плагины) — позволить ему управлять базами данных, вызывать API;
3. Структурированное выполнение — позволить ему шаг за шагом выполнять задачи по предустановленной логике, а не действовать по своему усмотрению.

Это основание для AI-агента (AI Agent): автоматизированного блока с целью, знаниями, инструментами и путем выполнения.

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image1.png)

> **Примечание:** Простые версии "агентов", о которых говорит индустрия, в основном относятся к усовершенствованным приложениям, составленным из комбинации LLM + инструменты + база знаний, а не к агентам с истинной самостоятельной планировкой. Хотя простые агенты не обладают истинной способностью рассуждения и долгосрочного планирования, они достаточны для поддержки множества сценариев автоматизации уровня предприятия. Мы дадим подробное введение в истинные агенты с самостоятельной планировкой и способностью действовать в последующих главах.

## 1.1 Самый простой агент: чат-бот вопрос-ответ на основе базы знаний

Определив множество ключевых навыков, которыми должен обладать агент, возникает достойный размышления вопрос: можно ли построить действительно полезный базовый агент, реализовав только одну из этих самых простых функций? Ответ положительный.

На самом деле, в большинстве практических бизнес-сценариев основное требование пользователей — это не автоматизация сложных операций AI (таких как вызов API или координация задач между системами), а предоставление точных и надежных ответов на основе собственных ресурсов предприятия. Это в точности соответствует первому из трех ключевых навыков агентов — способности предоставления знаний. Таким образом, мы приходим к самой простой и наиболее широко применяемой форме агента: чат-боту вопрос-ответ на основе базы знаний.

Хотя он еще не имеет возможностей вызова инструментов или самостоятельного планирования, его ключевое преимущество заключается в том, что ответы большой модели больше не генерируются из ничего, а имеют основу. Как это реализовать? Ключ в решении основной задачи: предприятия содержат огромное количество документов; когда есть тысячи страниц документов, как модель может быстро найти наиболее релевантный контент для каждого раунда разговора?

Решением является генерация с возможностью поиска (Retrieval-Augmented Generation, RAG).

Базовая идея RAG заключается в следующем: когда пользователь задает вопрос, система сначала получает из корпоративной базы знаний несколько текстовых фрагментов, наиболее семантически релевантных вопросу (например, определенный раздел из руководства продукта или определенное положение из политики HR), а затем эти фрагменты служат "контекстом", вводимым в большую модель, направляя ее генерировать ответы на основе реальных материалов.

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image2.png)

Источник изображения: [https://www.datacamp.com/blog/what-is-retrieval-augmented-generation-rag](https://www.datacamp.com/blog/what-is-retrieval-augmented-generation-rag)

Таким образом, ответы модели больше не основаны на обобщенных знаниях из ее обучающих данных, а привязаны к авторитетной информации, предоставленной предприятием. Цель RAG — посредством такого динамического введения внешних знаний значительно улучшить достоверность, точность и согласованность ответов — и даже позволить ответам "соответствовать персоне", например, отвечать с позиции клиентского обслуживания или в стиле технической документации.

В реальном бизнесе эта технология особенно важна, потому что большие модели часто "галлюцинируют". Например, если вы спросите как CFO или консультант о конкретных данных за определенный период, модель, вероятно, выдумает даты и события. С введением RAG надежность и управляемость ответов значительно улучшаются.

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image3.png)

Источник изображения: [https://www.databricks.com/glossary/retrieval-augmented-generation-rag](https://www.databricks.com/glossary/retrieval-augmented-generation-rag)

В практической части этого урока мы будем использовать популярную платформу AI-рабочих процессов Dify для построения чат-бота вопрос-ответ на основе знаний. Вы можете легко превратить различные типы собственных материалов, такие как руководства продукта, корпоративные политики, документацию проектов, исследовательские работы, статьи из баз знаний и даже личные заметки, в базу знаний.

После построения вы можете попробовать задать различные вопросы для проверки его возможностей, например:

- "Какие основные функциональные обновления в последней версии нашего продукта A?"
- "В соответствии с справочником сотрудников, каковы правила отпусков на этот год?"
- "Как мы решили техническую проблему 'XXX', с которой столкнулись в проекте XX?"
- "Какой основной метод исследования упоминается в этой статье?"

Вы лично почувствуете, как технология RAG преобразует статические разрозненные документы в точный интеллектуальный репозиторий знаний, обеспечивающий высокую точность ответов для различных сценариев.

## 1.2 От диалога к агентам и рабочим процессам

Однако даже с добавлением базы знаний или даже возможности вызова плагинов "расширенный агент" все еще недостаточен для более сложных бизнес-процессов.

Представьте себе запрос пользователя: "Какие новые функции были выпущены в нашем новом SaaS продукте? Можете ли вы организовать их в краткое резюме для наших клиентов?"

Этот запрос кажется простым, но требует нескольких скоординированных шагов: сначала получить записи о выпусках функций за последний месяц из внутренней документации продукта или базы знаний Notion; затем отфильтровать ключевые особенности, ориентированные на клиентов; затем вызвать большую модель для преобразования технического описания в язык, понятный клиентам; наконец, отправить созданный контент в почтовый ящик команды маркетинга или сохранить в шаблон Google Docs.

Если полагаться только на свободное рассуждение одной большой языковой модели, помимо вопроса о том, может ли она выполнить все это в одном разговоре, существует большой риск пропустить важную информацию, спутать внутреннюю терминологию с языком клиентов или не обеспечить структурированный вывод. Что более важно, предприятиям нужны проверяемые, повторно используемые, отслеживаемые стандартизированные пути выполнения, а не временные решения, зависящие от модели каждый раз. Управляемость и воспроизводимость очень важны для предприятий, и непредвиденные результаты могут привести к серьезным неожиданным потерям.

Это приводит нас к более продвинутой парадигме AI-приложений: AI-рабочие процессы (AI Workflow).

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image4.png)

Рабочий процесс — это разделение сложной задачи на несколько упорядоченных, конфигурируемых, автоматически выполняемых подшагов и оркестрирование логических отношений между ними посредством визуализации или кода, таких как условные суждения, циклы или параллельное выполнение. Преобразование AI-возможностей в SOP (то есть в стандартный операционный процесс) означает консолидирование опыта о том, как использовать AI для выполнения определенной задачи, в повторно используемый шаблон.

Этот подход приносит многочисленные преимущества: нетехнические люди (такие как менеджеры по продуктам или операционные специалисты) могут быстро построить AI-приложения путем перетаскивания компонентов; разработчики могут инкапсулировать поиск RAG, вызовы LLM, инструменты API и т.д. как стандартные узлы для повторного использования в различных бизнес-сценариях; весь процесс также может быть полностью отслежен, отлажен и непрерывно оптимизирован для соответствия требованиям предприятия в отношении стабильности и соответствия нормативным требованиям.

AI-рабочие процессы используют очень широкие группы пользователей. Менеджеры по продуктам могут проектировать полные пути взаимодействия пользователей без написания кода; операционные сотрудники могут быстро построить чат-ботов обслуживания, генераторы контента или системы уведомлений; разработчики и инженеры алгоритмов могут модульизировать основные способности для вызова фронтенда; предприниматели и независимые разработчики также могут проверить MVP AI-продукта с очень низкими затратами и развернуть полный прототип за несколько дней, включающий запрос данных, создание контента и выполнение действий.

Кроме того, стоит отметить, что AI-рабочие процессы обычно можно описать с помощью промежуточного представления (Intermediate Representation). Хотя конкретные способы выражения различаются между различными платформами рабочих процессов, большинство используют структурированные файлы (такие как JSON, YAML и т.д.) для определения типов узлов, входов/выходов и логики выполнения, структура которых похожа на приведенное ниже изображение:

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image5.png)

Вкратце, если агенты позволяют AI перейти от разговора к действию, то рабочие процессы позволяют AI перейти от случайного выполнения одного действия к "стабильному, надежному, масштабируемому выполнению целого класса действий". В следующей практике мы также будем использовать платформу Dify для построения полных AI-рабочих процессов и почувствуем полный цикл от идеи к работающему приложению.

## 1.3 Распространенные платформы агентов и рабочих процессов

С быстрым развитием генеративных AI-технологий растет число платформ, помогающих разработчикам и деловым людям быстро строить агентов и автоматизировать процессы, избегая сложности программирования. Появился набор платформ с низким кодом или без кода для агентов и рабочих процессов.

Во-первых, нужно уточнить: платформы низкого кода — это инструменты разработки, которые значительно снижают объем ручного кодирования благодаря визуальному перетаскиванию компонентов, предустановленным шаблонам бизнес-логики, конфигурированию графических правил и т.п. Суть в том, что визуальная конфигурация и узловое перетаскивание заменяют прямое написание кода, что позволяет как разработчикам с определенными техническими навыками избежать повторяющейся работы, так и нетехническим людям, знакомым с бизнес-логикой, участвовать в построении приложений. По сути, это мост между эффективностью разработки и гибкостью сценариев.

Выдающаяся ценность этого класса платформ — значительное снижение порога входа для разработки AI-приложений. Раньше требовалось несколько недель командной работы — от сбора требований до разработки кода и тестирования развертывания — чтобы завершить AI-агент (такой как чат-бот клиентского обслуживания, помощник обработки данных). Теперь, используя визуальные инструменты, предоставляемые платформой, цикл "от идеи к развертыванию" можно сократить до нескольких часов.

Основные платформы для работы с низким кодом AI на рынке в настоящее время включают:

| Платформа                                          | Характеристики                                               | Сценарии применения                               |
| --------------------------------------------- | -------------------------------------------------- | -------------------------------------- |
| Dify                                          | Открытый источник, поддержка RAG базы знаний, оркестровка LLM, вывод API, дружественный китайский язык | Вопрос-ответ на корпоративной базе знаний, настраиваемые агенты, API-сервисы |
| Coze (ByteDance)                              | Доступно внутри страны, интеграция с экосистемой Douyin/Feishu, богатые плагины              | Социальные боты, интеграция мини-программ внутри страны             |

| Baidu Qianfan AppBuilder / Alibaba Bailian / Tencent HunYuan | Облачные решения для больших компаний, интеграция собственных моделей                       | Корпоративное развертывание, сценарии с высокими требованиями к соответствию             |

Выбор платформ для работы с низким кодом AI на рынке в настоящее время богат. Хотя основные облачные провайдеры, такие как AWS, Azure и Alibaba Cloud, выпустили соответствующие решения для AI-рабочих процессов, Dify, Coze и n8n выделяются благодаря следующим трем основным преимуществам и стали наиболее широко применяемыми представителями:

1. Предельная простота использования. Платформы используют интуитивный визуальный интерфейс перетаскивания, пользователи не должны глубоко понимать базовые технологии и могут быстро начать работу.
2. Высокая гибкость. Поддержка пользовательских компонентов и расширения API-интерфейсов, может адаптироваться как к легким сценариям, таким как демонстрация преподавания и проверка MVP (минимально жизнеспособного продукта), так и к требованиям быстрого повторения для малых и средних команд.
3. Зрелая экосистема. Не только официальная документация детальна и оперативна, но и есть активное сообщество пользователей, удобно быстро получить предустановленные решения от разных пользователей.

Все три платформы поддерживают вывод построенного AI-агента в виде стандартизированного API-интерфейса, который может быть бесшовно интегрирован с веб-приложениями переднего плана, внутренними ERP-системами предприятия или мобильными приложениями, еще больше снижая технический порог развертывания AI-возможностей.

Dify позиционируется как платформа для разработки и операционализации приложений LLM, цель которой — обеспечить полный управление жизненным циклом приложений AI от концепции, развертывания до оптимизации. Платформа позволяет проектировать сложные потоки задач путем перетаскивания узлов и поддерживает создание агентов на основе намерений. Одновременно Dify совместима и поддерживает множество LLM, включая GPT, Claude и множество моделей открытого источника, построенные приложения могут быть развернуты одним кликом как стандартный API для удобной интеграции.

С точки зрения технической архитектуры, Dify характеризуется открытым источником и возможностью приватного развертывания, подчеркивающей гибкость, расширяемость и соответствие требованиям предприятия. Целевые пользователи включают команды разработчиков и бизнес-инноваторов, типичные сценарии применения охватывают интеллектуальное обслуживание клиентов и базы знаний предприятия, автоматизацию создания контента, AI-помощники для вертикальных областей и AI-платформу для предприятий.

# 2. Глубокое введение в Dify

## 2.1 Что такое Dify

Мы уже узнали базовую информацию о Dify ранее. Для более подробной информации вы можете посетить платформу Dify через [https://cloud.dify.ai/apps](https://cloud.dify.ai/apps). Если вы хотите узнать больше, посетите официальный веб-сайт https://dify.ai.

Dify — это платформа открытого источника для разработки LLM-приложений. Она предоставляет интуитивный интерфейс, объединяющий рабочие процессы агентов, конвейеры RAG, способности инструментов, управление моделями, наблюдаемость и другие функции, помогая вам быстро перейти от прототипа к производственной среде.

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image11.png)

Вы можете использовать большие языковые модели и различные инструменты в Dify для построения "рабочих процессов". Рабочий процесс — это превращение операций, которые вам нужно выполнить вручную шаг за шагом — таких как получение данных, вызов больших моделей, веб-поиск, фильтрацию результатов, форматирование выходных данных — в автоматизированный, повторно используемый процесс в соответствии с бизнес-логикой. Без рабочего процесса каждый раз нужно копировать-вставлять одно и то же содержимое в большую модель, что очень неэффективно, подвержено ошибкам и сложно для повторного использования в реальном бизнесе.

Построение рабочего процесса похоже на собирание кубиков или головоломок. Вы подключаете "узлы большой языковой модели" (отвечающие за понимание и генерацию), различные "узлы инструментов" (отвечающие за выполнение конкретных действий, такие как запрос к базам данных, отправка электронной почты, перевод текста и т.д.) и "узлы данных" (отвечающие за чтение и сохранение информации) как кубики. Они будут автоматически сотрудничать в соответствии с вашей предустановленной логикой, без необходимости ручного управления каждый раз. Вы также можете рассматривать это как "низкокодовую программу": вам нужно только конфигурировать пути ввода и вывода путем перетаскивания, чтобы реализовать довольно сложную бизнес-логику.

Например, если вы владелец магазина Amazon или Douyin e-commerce и хотите построить систему AI-обслуживания клиентов, вы можете разработать рабочий процесс, ориентируясь на приведенную ниже структуру:

1. Узел триггера (как START): получает вопрос пользователя, например "Как долго гарантия на этот товар?"
2. Узел классификации вопроса (как QUESTION CLASSIFIER): использует модель (например, GPT) для классификации вопроса пользователя, определяя, является ли это послепродажным вопросом (например, гарантия), вопросом об использовании или другим типом.
3. Узел получения знаний (как KNOWLEDGE RETRIEVAL): в зависимости от результата классификации, автоматически обращается к соответствующей базе знаний. Если это послепродажный вопрос о "гарантии", извлекает точную информацию о гарантии из базы знаний послепродажного SOP.
4. Узел большой языковой модели (LLM Node): отправляет вопрос пользователя и содержимое базы знаний вместе в большую языковую модель (например, GPT), позволяя ей создать ответ, дружественный к пользователю (избегая жесткого технического языка).
5. Узел условия: проверяет, содержит ли сгенерированный ответ ясное время гарантии (например, "1 год", "3 года"). Если да, переходит к следующему шагу. Если нет, попросить ответить "пожалуйста, предоставьте модель товара".
6. Узел вывода (как ANSWER): возвращает окончательный ответ пользователю и автоматически записывает эту консультацию в таблицу.

![](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image12.png)

На протяжении всего этого процесса вам не нужно вручную искать в базе знаний, много раз корректировать ответы модели или отдельно записывать данные — рабочий процесс будет "связывать эти шаги и автоматически работать". Кроме того, это очень гибко: например, если позже вы захотите добавить новое правило "когда пользователь спрашивает о диапазоне гарантии, вызовите другую базу знаний", вам нужно только добавить узел условия в рабочий процесс, без необходимости переструктурировать всю систему.

Это довольно простой пример рабочего процесса, но полное овладение этими способностями может быть для вас сейчас сложным. Поэтому в этом уроке мы начнем с более базового агента базы знаний и постепенно изучим более сложные техники рабочих процессов.

## 2.3 Поддержка пользовательских поставщиков моделей

Чтобы в полной мере использовать гибкость Dify — с учётом трудностей доступа к моделям в разных регионах и необходимости удовлетворить специфические бизнес-требования, контроль затрат или требования к конфиденциальности данных — нередко требуется подключить пользовательские модели. Dify поддерживает настройку трёх основных типов моделей: большие языковые модели (LLM), модели Embedding и модели Rerank. ## 2.4 Создание первой базы знаний Dify

![Страница Knowledge](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image30.png)

Затем нажмите `Create Knowledge` в левой части, чтобы создать свою первую базу знаний.

![Создание базы знаний](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image31.png)

На этой странице можно загружать файлы различных форматов (например, pdf, txt) для формирования базы знаний. Можно загружать длинные тексты или скопировать содержимое из Википедии и сохранить в виде txt-файла для загрузки. В данном примере мы загрузим txt-файл из Википедии об Илоне Маске.

После нажатия кнопки Next вы перейдёте на страницу Knowledge Base Settings (настройки базы знаний). Здесь много параметров — разберём их по порядку.

В разделе **General** находятся настройки «правил разбиения текста». Поскольку нам нужно разбивать длинный текст на небольшие фрагменты, сначала необходимо определить правила разбиения. На начальном уровне достаточно обратить внимание на **maximum chunk length (максимальная длина фрагмента)**. Попробуйте установить значение 512, 2048 или 4096, а затем нажмите **Preview Chunk**, чтобы увидеть результат при разных настройках.

Можно также настроить параметр **Chunk overlap (перекрытие фрагментов)**. Он определяет, будет ли между соседними фрагментами сохраняться некоторое количество общего контента. Умеренное перекрытие помогает избежать разрыва важной информации по разным фрагментам.

![Настройки разбиения](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image32.png)

В настройках также есть параметр **Chunk using Q&A format in English**. При включении система будет использовать большую языковую модель для преобразования части содержимого базы знаний в формат вопрос-ответ для хранения, что в некоторых сценариях может значительно улучшить качество поиска.

В реальном бизнесе выбор подходящей стратегии разбиения в зависимости от сценария позволяет лучше оптимизировать результаты поиска и гарантировать возврат ожидаемой информации.

Продолжайте прокручивать страницу вниз — вы увидите настройки, связанные с Embedding-моделью.

Поясним: основная функция Embedding-модели — преобразование неструктурированных данных (например, текста, изображений) в «числовые векторы» (Embedding-векторы), которые понимает компьютер. Благодаря этому преобразованию модель может быстро вычислять сходство между разными данными и находить семантически близкий контент — например, по фразе пользователя найти наиболее подходящий документ, изображение или товар.

Выбор Embedding-модели существенно влияет на конечный результат поиска (точность совпадения, скорость отклика и т. д.). Рекомендуется сначала попробовать Embedding-модель Qwen 0.6B; можно также переключиться на версии 4B или 8B и наглядно сравнить разницу в качестве поиска при разных масштабах параметров.

![Настройки Embedding](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image33.png)

Здесь вы также увидите ещё один параметр модели — **Rerank model**, по умолчанию **Jina-rerank-m0**. (Если вы не являетесь студентом кампуса, возможно, вы увидите ошибку об отсутствии Rerank-модели — для её использования необходимо настроить Rerank-модель в настройках.)

Основная функция Rerank-модели — выполнить второй, более точный ранжирование «предварительно отобранных кандидатов», чтобы наиболее подходящие результаты оказались выше, что значительно повышает релевантность итоговых результатов и удовлетворённость пользователей.

Простая аналогия: Rerank-модель решает проблему «недостаточной точности первичного отбора». Например, поисковая система может сначала найти 1000 потенциально релевантных страниц по простым правилам, а затем с помощью Rerank-модели выбрать из них 10 наиболее релевантных для показа на первой странице.

То же относится к рекомендательным системам: сначала может быть найдено 500 «потенциально подходящих» товаров, а Rerank-модель расставит их по порядку, поместив наиболее вероятные для покупки товары в начало списка.

![Rerank модель](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image34.png)

## 2.6 Создание первого Dify Workflow-приложения

Освоив основы построения диалоговых агентов в Dify, перейдём к созданию более сложных бизнес-рабочих процессов. Рабочий процесс — ключевой способ визуализации сложной бизнес-логики в Dify. С его помощью вы можете строить интеллектуальные потоки как конструктор, ощутить на практике, как информация перемещается между узлами, как развёртывается логика ветвлений, где расставляются точки ручного вмешательства и как в итоге формируется полноценный бизнес-результат.

Можно создать рабочий процесс с нуля или на основе шаблона. Ниже показано, как создать рабочий процесс с нуля:

![Создание Workflow 1](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image49.png)

![Создание Workflow 2](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image50.png)

Здесь вы увидите два варианта: Chatflow и Workflow. Как выбрать между ними? Ключевой вопрос: что является основой создаваемого вами процесса — непрерывный диалог или выполнение задач?

Chatflow создан специально для диалога. Он имитирует собеседника с памятью и пониманием контекста, отлично подходит для сценариев, требующих многоходовых взаимодействий и поддержания состояния. Например, в поддержке клиентов он связно понимает уточняющие вопросы пользователя — как терпеливый консультант. Потоковый вывод делает взаимодействие более естественным. Кратко: когда нужен агент, умеющий «разговаривать», выбирайте Chatflow.

Workflow ориентирован на автоматизированное выполнение процессов. Он похож на заранее настроенный конвейер: отлично справляется с задачами типа «один входной сигнал → несколько этапов обработки → детерминированный вывод». Например, ежедневное автоматическое создание отчётов, пакетная обработка файлов или цепочка вызовов API. Такие задачи обычно запускаются событием и не требуют интерактивного взаимодействия. Поэтому при необходимости реализовать «автоматизированные» задачи выбирайте Workflow.

Чтобы не ошибиться с выбором, ответьте на четыре ключевых вопроса:

1. Требует ли процесс выполнения нескольких вводов данных и корректировок от пользователя?
2. Нужно ли представлять результат поэтапно, в потоковом режиме?
3. Сильно ли логика обработки зависит от предыдущей истории взаимодействий?
4. Запускается ли задача событием, и являются ли входные/выходные данные однократными?

Если на первые три вопроса ответ «да» — Chatflow является идеальным выбором: типичные сценарии включают интеллектуальную поддержку клиентов, образовательное наставничество, совместное творчество и т. п. Если выражены характеристики четвёртого вопроса — выбирайте Workflow: он лучше подходит для очистки данных, создания отчётов, пакетной обработки и других сценариев автоматизации.

Здесь в качестве примера выберем Chatflow и нажмём на него, чтобы перейти в операционный интерфейс:

![Интерфейс Chatflow](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image51.png)

Кратко опишем интерфейс рабочего процесса. В центре — основной холст для редактирования, где вы визуально строите логику приложения. Как показано на рисунке, базовый рабочий процесс обычно начинается с узла START (для получения входных данных), данные по соединительным линиям передаются в узел LLM для обработки, а затем результат выводится через узел ANSWER. Каждый узел представляет функциональный модуль, а линии определяют порядок выполнения задач.

Вокруг холста расположена полная зона управления. В верхней части интерфейса — глобальные элементы управления: кнопка Preview для тестирования рабочего процесса и кнопка Publish для публикации. В углах холста — инструменты управления видом (масштаб, отмена действий) для точной настройки.

На левой панели сосредоточены функции управления приложением. Вкладка Orchestrate, на которой вы сейчас находитесь, используется для оркестрации процесса; после завершения разработки в разделе API Access можно получить данные для интеграции; Logs & Annotations записывает подробные следы каждого выполнения для отладки; а Monitoring предоставляет мониторинг производительности и состояния приложения в режиме реального времени.

Введите несколько слов в качестве системного промпта (SYSTEM) в узел LLM диалогового рабочего процесса, нажмите Preview и попробуйте запустить процесс. Убедитесь, что после изменения SYSTEM-промпта весь рабочий процесс меняется в соответствии с ожиданиями.

Нажмите правой кнопкой мыши на холсте и выберите «Add Node» для добавления узла, или просмотрите все доступные узлы на панели узлов слева:

Также можно открыть панель выбора инструментов и просмотреть все доступные инструменты:

Ниже краткое описание распространённых узлов и инструментов. Не нужно запоминать всё сразу — рекомендуется сначала получить общее представление, постепенно знакомиться с ними на практике и возвращаться к этому разделу при необходимости.

1. Узлы LLM и вывода

![Узлы LLM 1](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image54.png)

![Узлы LLM 2](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image55.png)

Эти узлы отвечают за основные процессы в рабочем потоке.

- Узел LLM: ключевой вычислительный блок для вызова большой языковой модели. Фокус настройки — проектирование промптов и тонкая настройка параметров, превращающие бизнес-задачу в инструкции для модели.
- Узел Knowledge Retrieval: блок поиска в базе знаний, извлекает из заданной базы знаний или внешних авторитетных источников информацию, релевантную бизнес-вопросу. Обеспечивает узел LLM точными знаниями и помогает снизить «галлюцинации».
- Узел Answer: блок вывода результатов, принимает обработанный LLM контент и организует его в итоговый результат, соответствующий нуждам бизнес-сценария. Фокус настройки — определение формата вывода (шаблоны формулировок, стандарты оформления).
- Узел Agent: блок принятия высокоуровневых решений. Не просто вызывает модель, но может выполнять многошаговое планирование и самостоятельно выбирать и вызывать внешние инструменты. Подходит для сложных цепочек задач, требующих динамических решений.
- Узел Question Classifier: блок классификации вопросов, распознаёт и категоризирует входящие вопросы (по намерению, тематической области и другим критериям), помогая последующим процессам точно сопоставить соответствующие узлы обработки (разные типы вопросов → разные LLM-промпты или инструментальные цепочки).

2. Узлы логики и управления потоком

![Узлы управления потоком](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image56.png)

Эти узлы определяют маршруты выполнения и правила рабочего процесса.

- Условные узлы: например, `IF/ELSE` — реализуют ветвление процесса через булевы условия. Ключевое при проектировании — строгость условных выражений, обеспечивающих покрытие всех бизнес-сценариев.
- Узел Iteration: безсостоятельный блок параллельной пакетной обработки. Предназначен для сценариев, где подзадачи не зависят друг от друга и могут обрабатываться независимо — например, пакетный перевод абзацев, параллельная проверка нескольких фрагментов контента или одновременная генерация нескольких отчётов. Узел принимает входной массив, автоматически разбивает его на части и параллельно отправляет каждый элемент по одной и той же цепочке обработки. Внутри итерации к текущему элементу можно обратиться через `{{item}}`, к индексу — через `{{index}}`; результаты автоматически объединяются в массив. При настройке важно задать степень параллелизма для баланса эффективности и нагрузки на систему, а также определить стратегии повтора и обработки сбоев для стабильной пакетной обработки.
- Узел Loop: состоятельный рекурсивный итератор. Подходит для сценариев, где результат зависит от предыдущего шага — многоходовая оптимизация параметров, рекурсивное улучшение контента (повторные правки текста до достижения нужного результата) или цепочные вычисления на основе предыдущего результата. Ключевой элемент — «переменная состояния»: она должна быть инициализирована до начала цикла (например, счётчик итераций, промежуточный результат) и явно обновляться в каждой итерации как входные данные следующей. Во избежание бесконечного цикла необходимо определить условие завершения (счётчик «максимум 10 итераций», результатное условие «оценка удовлетворённости > 9», внешний сигнал «обнаружен ввод "стоп"»), а также задать тайм-аут и маршруты обработки исключений.

3. Узлы операций с данными и интеграции

![Узлы данных](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image57.png)

- Узел Code: блок обработки кода, выполняет пользовательский код внутри рабочего процесса — преобразование форматов данных, сложные вычисления и другие нестандартные задачи. Фокус настройки — корректность синтаксиса кода и совместимость со средой выполнения.
- Узел Template: блок обработки шаблонов, подставляет динамические данные в заданный шаблон для создания контента требуемого формата (кастомизированные тексты, структуры отчётов). Фокус — синтаксис шаблона и правила сопоставления переменных.
- Узел Variable Aggregator: блок агрегирования переменных, собирает переменные из выходов нескольких узлов рабочего процесса и объединяет рассредоточенные данные в единый набор. Фокус — область агрегируемых переменных и правила объединения данных.
- Узел Doc Extractor: блок извлечения из документов, извлекает текст, таблицы и другой ключевой контент из PDF, Word и других документов, преобразуя их в структурированные данные для рабочего процесса. Фокус — совместимость с форматами документов и правила фильтрации контента.
- Узел Variable Assigner: блок присваивания переменных, определяет, инициализирует или обновляет переменные в рабочем процессе, обеспечивая основу для передачи данных. Фокус — именование переменных, типы данных и логика присваивания.
- Узел Parameter Extractor: блок извлечения параметров, извлекает указанные параметры из запросов пользователей, ответов интерфейсов и других входных данных, преобразуя неструктурированную информацию в структурированные данные. Фокус — настройка правил извлечения (регулярные выражения, JSON-пути).
- Узел HTTP Request: блок HTTP-запросов, инициирует HTTP-запросы (GET, POST и другие методы) к интерфейсам внешних систем, обеспечивая обмен данными рабочего процесса с внешними сервисами. Фокус — адрес запроса, метод и настройка параметров/заголовков.
- Узел List Operator: блок операций со списками, выполняет операции с данными типа массив/список (фильтрация, сортировка, разбиение) для адаптации структуры данных к последующим процессам. Фокус — тип операции (условия фильтрации, правила сортировки).

### 2.6.2 Описание распространённых инструментов

![Панель инструментов Dify](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image58.png)

В Dify большинство инструментов можно напрямую разместить на холсте как узлы и соединять с предыдущими и последующими узлами, как любые другие: при корректных входных данных согласно спецификации параметров узла (инструмента) он нормально выполнится и выдаст результаты, которые можно передать дальше.

На панели узлов слева или справа можно просмотреть все доступные инструментальные узлы; дополнительные инструменты можно добавить через маркетплейс плагинов. Краткое описание нескольких распространённых инструментов:

- Инструмент веб-поиска
  В качестве примера — Tavily Search: обеспечивает большую модель оптимизированными для AI возможностями поиска в реальном времени.
  Возвращает структурированные результаты поиска (заголовок, аннотация, ссылка и т. д.), которые можно напрямую использовать как часть промпта LLM для ответов на актуальные новостные вопросы или вопросы, требующих авторитетного источника.
- Инструменты обработки данных
  Например, плагин JSON Process — для выполнения расширенных операций с JSON-данными: запрос, фильтрация, преобразование, объединение.
  При работе со сложными API-ответами или многоуровневыми вложенными данными логику «очистка + реструктуризация данных» можно поручить этому инструменту, упрощая ручное написание парсинг-кода в узлах Code.
- Инструменты форматирования
  Например, Markdown Exporter — экспортирует сгенерированный контент в заданном формате (Markdown-документ, шаблоны оформления), для дальнейшего использования в презентациях, отчётах или интеграции в другие системы.

В списке инструментов можно видеть количество установок и краткое описание каждого плагина. На начальном этапе рекомендуется сначала попробовать инструменты из раздела «Featured / Рекомендованные» — они обычно охватывают наиболее распространённые бизнес-сценарии.

Использование инструментов обычно требует определённого опыта. Рекомендуется сначала поискать в поисковике «официальные примеры DSL рабочего процесса» для конкретного инструмента, импортировать готовый пример и использовать его — это естественным образом сэкономит много времени по сравнению с самостоятельным построением с нуля.

### 2.6.3 Создание простого рабочего процесса классификации намерений

К этому моменту у нас уже есть базовое представление об основах Dify Workflow и инструментах, но без практики мы никогда не сможем в полной мере овладеть деталями. Нам нужен «гипотетический» реальный бизнес-сценарий для тренировки.

Например, в реальном сценарии покупок пользовательский ввод никогда не бывает «чётко структурированными параметрами» — это всегда обычная разговорная фраза: кто-то пришёл сделать заказ, кто-то пожаловаться, кто-то просто поболтать, а кто-то совсем не по теме. Если весь этот ввод напрямую передавать одной большой языковой модели, обычно возникают две типичные проблемы:

1. Непоследовательный стиль ответов
   На одну и ту же жалобу LLM иногда извинится и успокоит, а иногда начнёт «объяснять причины»; на один и тот же заказ иногда уточнит недостающие детали, а иногда придумает заказ.
2. Неконтролируемая бизнес-логика
   Вы хотите, чтобы «при жалобе обязательно сначала извинились», но модель не всегда соблюдает это правило; вы хотите, чтобы «нетематические вопросы перенаправлялись обратно в основную тему», но модель может с энтузиазмом обсуждать анекдоты.

Поэтому более инженерный подход — разбить задачу на стандартизированный конвейер: сначала классифицировать намерение (определить, что именно хочет пользователь), затем маршрутизировать по намерению (использовать разные промпты и роли для разных сценариев), и наконец унифицировать упаковку вывода ответов LLM после маршрутизации (для удобства интеграции на фронтенде или в системе).

Цель этого раздела — научить систему обрабатывать несколько типов диалогов в ресторанном сценарии. Рекомендуется выполнить это практическое задание для закрепления знаний. Сначала определим сценарии как классификацию намерений:

- **Заказ еды (buy_food)**: пользователь явно выражает намерение купить.
- _Пример: «Дайте мне набор с жареной курицей и стакан колы.»_
- **Жалоба (complain)**: пользователь выражает недовольство, торопит или даёт негативный отзыв.
- _Пример: «Вы слишком медленные! Жду уже час.»_
- **Болтовня/консультация (chitchat)**: пользователь задаёт открытые вопросы, ищет советы, но без чёткого намерения сделать заказ.
- _Пример: «Что бы поесть сегодня, что посоветуешь?»_
- **Прочее (other)**: ввод пользователя не связан с ресторанным сценарием.
- _Пример: «Помоги мне написать смешной текст для публикации.»_

Для этих четырёх намерений мы задаём четыре разные «коммуникационные личности», каждую из которых выполняет отдельный узел LLM — каждый узел исполняет роль LLM с разными личностными установками.

- **Помощник по заказам (LLM_BuyFood)**: профессиональный, эффективный; ключевая задача — подтвердить детали заказа и активно уточнить недостающую информацию.
- **Специалист поддержки (LLM_Complain)**: эмпатичный, выдержанный; главная задача — успокоить пользователя и предложить чёткое решение.
- **Собеседник (LLM_Chitchat)**: лёгкий, дружелюбный; цель — дать персонализированные рекомендации и стимулировать потенциальные покупки.
- **Вежливый привратник (LLM_Other)**: сосредоточенный, с чёткими границами; отвечает за вежливое перенаправление вышедших за тему диалогов обратно к основному бизнесу.

#### Проектирование оркестрации рабочего процесса

Теперь спроектируем оркестрацию рабочего процесса — определим, какие узлы понадобятся. Для новичков сложно сразу придумать нужные узлы (да и опытным специалистам лень думать самостоятельно — попросить большую модель дать совет обычно самый быстрый и лучший вариант). Поэтому воспользуемся большой моделью для получения рекомендаций по оркестрации. Ключевая структура узлов такова:

- Start (Начало): точка входа данных, получает исходный ввод пользователя `user_text`.
- Question Classifier (Классификатор намерений): «мозг» и «диспетчерский центр» рабочего процесса. Анализирует `user_text` и выбирает наиболее подходящую метку из четырёх заданных намерений.
- Condition (Условное ветвление): играет роль «переключателя потока». На основе метки намерения от классификатора направляет задачу по соответствующему специализированному маршруту.
- Четыре параллельных узла LLM (LLM_BuyFood, LLM_Complain, LLM_Chitchat, LLM_Other): четыре независимых «экспертных блока». Каждый получает исходный вопрос, но генерирует совершенно разные ответы по стилю и цели согласно своему уникальному системному промпту.
- Variable Aggregator (Агрегатор переменных): после обработки по нескольким маршрутам нужна «точка сбора». Этот узел собирает ответ из единственного активированного ветвления в единую переменную `final_reply`, обеспечивая стабильность структуры вывода.
- Output (Конец): последняя точка выхода, выводит метку намерения, исходный вопрос и сгенерированный ответ в структурированном виде (например, JSON) для последующего системного вызова или отладки.

- `buy_food`: пользователь явно хочет купить еду, сделать заказ.
- `complain`: пользователь жалуется, возмущается или злится, обычно выражает недовольство.
- `chitchat`: пользователь болтает, обсуждает, что поесть, или просит рекомендацию.
- `other`: не связано с ресторанным сценарием или трудно определить намерение.

Кроме того, нужно написать промпт в разделе ADVANCED SETTING, чтобы большая модель могла корректно классифицировать по вводу пользователя. Пример промпта:

```
Выберите одну наиболее подходящую метку из buy_food / complain / chitchat / other. Если пользователь жалуется и одновременно делает заказ, следует определить его ключевую эмоцию: если акцент на выражении недовольства — отнести к complain. Если жалоба незначительная, а основное намерение — сделать заказ — отнести к buy_food. Если действительно трудно определить — использовать other как запасной вариант.
```

![Настройка классификатора](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image62.png)

После настройки можно запустить отдельное тестирование этого узла, нажав кнопку воспроизведения в правом верхнем углу:

![Тестирование узла 1](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image63.png)

![Тестирование узла 2](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image64.png)

Судя по результатам в OUTPUT, классификация верная. Можно протестировать разные типы ввода, чтобы проверить стабильность классификатора.

Далее нужно подключить к классификатору последующие выходы большой модели. Например, когда `label` равен `"buy_food"`, рабочий процесс точно переходит к узлу `LLM_BuyFood`. Создадим четыре узла LLM с разными системными промптами; различие в системных промптах определяет разный стиль ответов.

- LLM_BuyFood (Помощник по заказам):

Ты помощник по заказу еды. Требования: 1. Подтверди, что хочет заказать пользователь. 2. Если информация неполна, вежливо уточни. 3. Тон вежливый и краткий.

- LLM_Complain (Специалист поддержки):

Ты специалист поддержки ресторана, занимаешься жалобами. Требования: 1. Искренне извинись. 2. Кратко объясни возможные причины (не перекладывай ответственность). 3. Предложи чёткое следующее решение.

- LLM_Chitchat (Собеседник):

Ты маленький помощник по выбору еды. Требования: 1. Лёгкий и дружелюбный тон. 2. Дай 1–3 простых рекомендации. 3. Если у пользователя нет предпочтений, предложи варианты разных стилей.

- LLM_Other (Вежливый привратник):

Ты небольшой помощник ресторана, специализирующийся только на темах, связанных с едой. Когда пользователь говорит о чём-то несвязанном: 1. Вежливо объясни свою область компетенции. 2. Направь пользователя обратно к основному сценарию.

Важно: в каждом узле после заполнения параметров SYSTEM-промпта не забудьте включить таблицу параметров USER-промпта. В ней нужно нажать символ `{x}`, выбрать параметр `user_text` как пользовательский ввод и добавить перед ним метку `user input:`, обозначающую, что эта переменная — ввод пользователя. При ответе будет учитываться и исходный ввод пользователя, и встроенный промпт.

Для проверки нажмите стрелку воспроизведения в правом верхнем углу узла и проведите тестовый диалог (например, «хочу заказать жемчужный чай с молоком») — проверьте, соответствует ли ответ ожиданиям.

![Тестирование LLM узла](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image65.png)

Далее обработаем выходные значения параллельных LLM. В панели конфигурации узла `Variable Aggregator` найдите область `ASSIGN VARIABLES` (присвоение переменных) и последовательно добавьте туда ответы каждой большой модели.

![Variable Aggregator](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image66.png)

Далее нужно агрегировать все выходные данные и получить желаемый результат: ввод пользователя, классификацию и ответ. Поскольку мы используем Workflow, а не Chatflow, узла Answer для агрегации результатов нет. Вместо него выберем узел Template: укажите в разделе переменных результат классификации намерений, ввод пользователя и итоговый ответ от агрегатора переменных; в CODE напишите шаблон финального ответа в формате JSON:

- `intent` ← `class_name`
- `original_text` ← `user_text`
- `final_reply` ← `variable_aggregator`

```
{
  "intent": "{{ intent }}",
  "original_text": "{{ original_text }}",
  "reply": {{ final_reply }}
}
```

![Template узел](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image67.png)

Наконец добавьте выходной узел output — все операции завершены:

![Output узел](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image68.png)

#### Тестирование работы рабочего процесса

Готово! Попробуем запустить этот рабочий процесс. Он способен демонстрировать совершенно разные модели поведения в зависимости от ввода:

- Ввод (заказ): «Дайте мне набор с острой куриной котлетой и большую колу.»
  - Маршрут: `buy_food` → `LLM_BuyFood`
  - Ответ: «Хорошо, набор с острой куриной котлетой и большая кола записаны. Хотите ли вы заменить картошку фри в наборе?»
- Ввод (жалоба): «Вы слишком медленные! Жду уже больше часа!»
  - Маршрут: `complain` → `LLM_Complain`
  - Ответ: «Очень сожалеем, что вам пришлось так долго ждать. Это действительно наша оплошность, и мы понимаем, как это неприятно. Мы срочно проверяем статус доставки вашего заказа и договоримся о соответствующей компенсации. Спасибо за ваше терпение.»
- Ввод (болтовня): «Что бы поздоровее поесть сегодня?»
  - Маршрут: `chitchat` → `LLM_Chitchat`
  - Ответ: «Для здорового питания можно попробовать наши лёгкие салаты или куриную грудку с овощами. Вы предпочитаете что-то лёгкое или чуть более сытное? Могу дать более конкретные рекомендации.»
- Ввод (нерелевантный): «Придумай мне анекдот для завтрашнего совещания.»
  - Маршрут: `other` → `LLM_Other`
  - Ответ: «Звучит интересно! Но я в основном специализируюсь на рекомендации еды и помощи с заказами. Если вы хотите угостить себя чем-нибудь вкусным после тяжёлого рабочего дня — я всегда готов помочь!»

> **Скрытая ошибка:** Если вы столкнётесь со странными проблемами, связанными с `aggregation group`, это, скорее всего, встроенная ошибка Dify. Она может возникнуть при определённых операциях: если вы когда-либо включали, а потом отключали AGGREGATION GROUP, система могла создать конфигурацию группы с остаточными аномальными параметрами. Даже если переключатель выглядит выключенным, эти остатки могут вызвать проблемы — например, ошибки, связанные с параметром `any`. В этом случае просто удалите узел и создайте его заново.

После запуска в Test Run можно видеть ход выполнения рабочего процесса: он прошёл по правильному маршруту согласно классификации и получил итоговый результат output. На этом весь процесс завершён.

![Результат выполнения](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image69.png)

## 2.8 Dify как поставщик API

Далее попробуем вызвать только что созданного агента с базой знаний через API — мы хотим превратить Dify в централизованный бэкенд для работы с большой моделью.

Помните, как раньше мы вызывали модели через API? Нужно подготовить ключ (Key) и пример вызова API (примеры request/response из документации), передать всё это большой модели и попросить её написать код для вызова сервиса, а также извлечь из результата нужные поля.

На этот раз мы воспользуемся локальным редактором кода [Trae](https://www.trae.cn/) для выполнения этого процесса.

Если вы ещё не знакомы с понятием IDE, сначала прочитайте документ [Extra Knowledge 4 - What is AI IDE and Trae](https://github.com/datawhalechina/easy-vibe/blob/main/docs/extra/extra4/extra4-what-is-ai-ide-and-trae.md).

Если локальная среда разработки ещё не настроена полностью — не беспокойтесь. Пока вы доверяете своему кодовому помощнику (будь то [z.ai](http://z.ai) или Trae), при любом непонятном моменте или ошибке можно просто описать проблему ему — он даст подробное решение.

![Боковая панель Trae](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image79.png)

После открытия боковой панели вы увидите опцию `Builder`. Это режим Agent. Можно просто понимать «Builder» как «режим разработки» [z.ai](http://z.ai): он тоже умеет управлять локальным компьютером, устанавливать зависимости, открывать веб-страницы и т. д.

# 3. Дополнительные примеры бизнес-рабочих процессов

Можно поискать в поисковых системах по ключевым словам вроде `Dify workflow примеры` или найти на GitHub репозитории с примерами Dify-рабочих процессов (качество варьируется — изучите несколько разных репозиториев). Конечно, рабочий процесс — это не что иное, как отображение бизнес-SOP: подумайте, какие рутинные или учебные процессы в вашей повседневной работе можно закрепить в рабочем процессе.

Ниже приведены примеры дизайнов рабочих процессов, сгенерированных большой моделью (реальные реализации во многом аналогичны; человеческий дизайн рабочих процессов, как правило, менее изящен, чем дизайн большой модели, за исключением работ опытных специалистов). Если какая-то идея покажется вам интересной, отправьте её большой модели для дальнейшей детализации — пусть она предложит конкретную настройку узлов Dify и детали реализации.

## 3.1 Рабочие процессы для социальных сетей

1. Рабочий процесс одним кликом распространяет контент на разных платформах (сложный)
   1. Идея: берём один основной материал как «сырьё» и автоматически обрабатываем его в «готовую продукцию» для нескольких платформ.
   2. Реализация: `Start` вводит статью -> `LLM` полирует -> несколько параллельных узлов `LLM` (каждый играет роль эксперта конкретной платформы, например «эксперт по вирусным текстам Xiaohongshu», «профессиональный автор Zhihu») -> узел `Iterator` обрабатывает требования разных платформ -> `Variable Aggregator` агрегирует -> `Answer` выводит все версии. Сложность — в параллельной обработке и итерации.
2. Генератор выбора тем по трендам и черновиков (средний)
   1. Идея: автоматически отслеживает тренды, быстро генерирует темы и черновики контента.
   2. Реализация: `Start` вводит ключевые слова -> узел `Tool` вызывает API поисковика для получения трендов -> `LLM` суммирует 3–5 тем -> `LLM` генерирует план или черновик статьи. Сложность — в интеграции внешних инструментов и фильтрации информации.
3. Умный помощник по классификации и ответам в комментариях (сложный)
   1. Идея: автоматически анализирует эмоции и намерения в комментариях, генерирует предложения по категоризированным ответам.
   2. Реализация: узел `HTTP Request` подключается к API соцсетей -> узел `Question Classifier` или `LLM` выполняет многоуровневую классификацию (позитивное, вопрос, жалоба, реклама и т. д.) -> узел `Condition` маршрутизирует к разным цепочкам генерации ответов -> параллельные узлы `LLM` генерируют персонализированные черновики -> `Answer` выводит. Сложность — в условном ветвлении и реальном вызове API.
4. Автогенератор сценариев и раскадровки для коротких видео (сложный)
   1. Идея: по теме или описанию продукта автоматически генерирует сценарий, описание раскадровки и рекомендованные теги.
   2. Реализация: `Start` вводит тему -> `LLM` генерирует творческий сценарий -> второй узел `LLM` разбивает сценарий на последовательность сцен (описание кадра, текст, длительность) -> узел `Tool` вызывает сервис текст-в-речь для генерации аудиосэмплов -> `Variable Aggregator` объединяет элементы -> `Answer` выводит структурированный файл сценария. Сложность — в многошаговой последовательности и интеграции внешних сервисов.
5. Помощник реального времени для суммирования вопросов из прямого эфира (средний)
   1. Идея: обрабатывает текстовые комментарии в реальном времени, выделяет ключевые вопросы и обратную связь.
   2. Реализация: узел `HTTP Request` получает комментарии в потоке -> узел `Iterator` обрабатывает пакеты данных временными окнами -> узел `LLM` суммирует горячие вопросы и эмоциональные тенденции -> узел `Answer` или `Webhook` выводит резюме стримеру. Сложность — в обработке потоковых данных в реальном времени и цикловых окнах.

## 3.2 Рабочие процессы для работы

1. Умная система ведения протоколов совещаний и автоматического распределения задач (сложная)
   1. Идея: извлекает протокол из текста записи совещания и автоматически создаёт задачи.
   2. Реализация: `Start` вводит текст совещания -> `LLM` суммирует темы и выводы -> узел `Parameter Extractor` точно извлекает action items (задача, ответственный, срок) -> `LLM` объединяет в письмо с протоколом -> параллельные узлы `HTTP Request` вызывают API Jira/Trello/Feishu для создания задач. Сложность — в извлечении информации и связи с несколькими системами.
2. Помощник пакетного скрининга и оценки резюме (средний)
   1. Идея: автоматически разбирает резюме, оценивает соответствие и генерирует вопросы для интервью.
   2. Реализация: `Start` загружает резюме и JD -> узел `Document Extractor` разбирает текст резюме -> `LLM` в роли HR оценивает соответствие -> для высокооцениваемых кандидатов другой `LLM` генерирует углублённые вопросы. Сложность — в разборе документов и многоусловной оценке.
3. Одноразовый перевод многоязычной электронной почты и черновик ответа (простой)
   1. Идея: автоматически переводит письмо и составляет черновик ответа.
   2. Реализация: `Start` вводит письмо -> `LLM` определяет язык и переводит -> `LLM` обдумывает ключевые пункты ответа -> `LLM` переводит на исходный язык и полирует. Основано на последовательном вызове LLM.
4. Автоматический сбор данных и генерация инсайтов для еженедельных/ежемесячных отчётов (сложная)
   1. Идея: подключается к нескольким источникам данных, автоматически генерирует структурированные рабочие отчёты.
   2. Реализация: несколько параллельных узлов `HTTP Request`/`Tool` вызывают API бизнес-систем (CRM, Git, инструменты управления проектами) -> узел `Code` или `LLM` очищает и обрабатывает данные -> `LLM` анализирует тренды, достижения и риски, генерирует повествовательный отчёт -> `Answer` выводит документ с текстом и визуализацией. Сложность — в агрегировании данных из нескольких источников и сочетании обработки данных с умным анализом.
5. Умная проверка контрактов/документов и извлечение ключевых пунктов (средний)
   1. Идея: быстро проверяет юридические или коммерческие документы, выявляет риски и извлекает ключевые положения.
   2. Реализация: `Start` загружает PDF контракта -> `Document Extractor` извлекает текст -> узел `LLM` (в роли юридического эксперта) проверяет ответственность, условия оплаты, штрафные санкции и т. д. -> узел `Parameter Extractor` извлекает структурированные данные: ключевые даты, суммы, стороны -> `Answer` выводит предупреждения о рисках и таблицу ключевых пунктов. Сложность — в обработке длинных документов и извлечении структурированной информации.

## 3.3 Рабочие процессы для обучения и жизни

1. Глубокий анализатор научных статей и генератор заметок (сложный)
   1. Идея: загружаем PDF статьи, автоматически генерируем структурированные заметки.
   2. Реализация: `Start` загружает PDF -> `Document Extractor` извлекает полный текст -> несколько параллельных узлов `LLM` по разным задачам суммируют аннотацию, метод, находки, список литературы -> `Variable Aggregator` объединяет -> `Answer` выводит заметки в формате Markdown. Сложность — в параллельной обработке разных частей длинного текста.

2. Персонализированный планировщик путешествий (средний)
   1. Идея: на основе предпочтений пользователя автоматически составляет подробный маршрут.
   2. Реализация: `Start` вводит требования (место, дни, бюджет, интересы) -> узел `Tool` вызывает поисковик или API карт для получения информации о местах -> `LLM` объединяет информацию и составляет ежедневный маршрут (с временем, активностями и оценкой бюджета). Сложность — в получении внешней информации и структурированном планировании.

3. Интерактивный партнёр для изучения иностранного языка (простой)
   1. Идея: создаём диалогового бота для ролевых игр и исправления грамматики.
   2. Реализация: системный промпт задаёт роль AI -> `Start` принимает фразу пользователя -> `LLM` выполняет две задачи: ответ в роли + исправление грамматики с пояснением -> `Answer` выводит. Ключ — в многозадачных инструкциях для LLM.

4. Персональная система Q&A по базе знаний с рекомендацией ссылок (сложная)
   1. Идея: на основе сохранённых документов, заметок, веб-ссылок создаём умную систему, которая отвечает на вопросы и рекомендует связанные старые знания.
   2. Реализация: оффлайн-обработка: используем `Document Extractor` и инструмент `Embedding` для нарезки и векторизации личной базы знаний. Онлайн-рабочий процесс: `Start` вводит вопрос -> узел `Retrieval` находит наиболее релевантные фрагменты -> `LLM` генерирует ответ на основе найденного контекста -> параллельно другая ветвь использует найденный контент как входные данные, `LLM` генерирует список рекомендаций «связанных старых знаний» -> `Answer` объединяет ответ и рекомендации. Сложность — в построении RAG-потока.

5. Консультант по отслеживанию и корректировке планов питания и фитнеса (средний)
   1. Идея: на основе ежедневного журнала питания и тренировок предоставляем анализ питания и советы.
   2. Реализация: `Start` вводит текстовый журнал (например, «обед: куриная грудка 150 г, рис одна порция, овощи; тренировка: приседания 5 подходов») -> узел `Parameter Extractor` структурирует вводные данные -> `LLM` в роли фитнес-тренера анализирует, сбалансировано ли питание и адекватна ли нагрузка -> сравнивает с долгосрочными целями, даёт рекомендации по коррекции. Сложность — в извлечении структурированной информации из неструктурированного журнала и персонализированной обратной связи.

# 6. Ограничения платформ рабочих процессов

Платформы рабочих процессов (или low-code платформы) — не универсальное решение. Несмотря на то что они удобны для бизнес-пользователей и снижают порог прямого программирования, с другой стороны, «low-code» нередко означает и «high-code» — пользователям всё равно нужно понимать концепции, правила и логику работы платформы, что само по себе создаёт новые обучающие затраты.

Возможно, вы задумаетесь: многие простые рабочие процессы — это по сути последовательные вызовы обёрнутых функций большой модели, где вывод одной функции становится вводом следующей. По сути это решается несколькими строками кода — зачем нужна такая сложная многоуровневая обёртка, которая ещё и усложняет вызовы API?

Вы правы. В условиях быстрого развития vibe coding — с возможностями генерации кода AI — иногда читать или генерировать код напрямую может быть эффективнее. В идеале хотелось бы управлять логикой приложений на естественном языке — вот что такое современная программная платформа. Но сегодняшние платформы рабочих процессов этого ещё не достигли, поэтому между намерением пользователя и конечной реализацией неизбежно существует «промежуточный слой». Освоение этого промежуточного слоя — именно та стоимость обучения, в которую нужно вложить время. В идеале будущие платформы рабочих процессов должны поддерживать полную AI-управляемость через диалог, чтобы AI реально управлял построением рабочего процесса и каждой деталью его параметров.

Тем не менее уверенное использование таких платформ постепенно становится базовым навыком — как офисные программы Microsoft: очень распространены и практичны в бизнесе, стоят того, чтобы их освоить.

В последующих продвинутых курсах мы рассмотрим, как строить рабочие процессы и RAG-решения на уровне кода. Тогда вы сможете лично ощутить разницу в сложности и гибкости между разными подходами к реализации. (Стоит отметить, что для некоторых простых диалоговых приложений или вложенной логики реализация через рабочий процесс может и не быть сложной.)

# [Исправление ошибки] Решение проблем с HTTP-запросами

Если вы столкнулись с проблемой, изображённой на рисунке ниже, обратитесь к этому разделу. В противном случае можно его пропустить.

Иногда вы можете развернуть Dify на собственном сервере, но внешний адрес сервера обычно работает по протоколу HTTP, а не HTTPS. Когда вы обращаетесь к сервису, поддерживающему только HTTP, может появиться сообщение примерно следующего содержания (откройте режим отладки браузера F12, чтобы найти проблемный элемент):

![HTTP ошибка](https://raw.githubusercontent.com/datawhalechina/easy-vibe/main/docs/zh-cn/stage-2/ai-capabilities/dify-knowledge-base/images/image98.png)

Причина этой проблемы в том, что по умолчанию Dify развёртывается на сервере, поддерживающем только HTTP, а не HTTPS. HTTPS (HyperText Transfer Protocol Secure) — это HTTP с добавленным уровнем шифрования SSL/TLS; проще говоря, это «более безопасная версия HTTP».

Чтобы сервис поддерживал HTTPS, обычно можно:

- использовать другую программу для перенаправления запросов (например, настроить обратное проксирование на nginx с сертификатом), или
- привязать доменное имя и запросить сертификат для него.

Но эти операции довольно сложны. Здесь мы используем Zeabur в качестве шлюза перенаправления для решения проблемы.

По умолчанию веб-страницы Zeabur доступны по HTTPS, поэтому нужно лишь перенаправить исходный адрес запроса на домен Zeabur — и проблема решена.

- Исходный адрес: `http://{DIFY_API_URL}/v1/chat-messages`
- Новый адрес: `https://{DIFY_NEW_API_URL}.zeabur.app/v1/chat-messages`

Просто замените доменную часть URL (публичный IP или доменное имя) на развёрнутый домен Zeabur — мы заранее настроили перенаправление в сервисе.

При желании можно самостоятельно развернуть сервис перенаправления на Zeabur. При создании сервиса на Zeabur выберите Python и вставьте следующий Python-код. После развёртывания получите адрес с HTTPS, который будет работать корректно.

После развёртывания в настройках сети установите порт прослушивания программы на 8080 и откройте его для внешнего доступа.

Примечание: замените `{DIFY_API_URL}` на фактический адрес Dify API.

```python
from flask import Flask, request, Response
import requests

app = Flask(__name__)

TARGET_BASE_URL = "{DIFY_API_URL}"
LISTEN_PORT = 8080

@app.route('/', defaults={'path': ''}, methods=['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS', 'HEAD'])
@app.route('/<path:path>', methods=['GET', 'POST', 'PUT', 'DELETE', 'PATCH', 'OPTIONS', 'HEAD'])
def proxy_request(path):
    target_url = f"{TARGET_BASE_URL}/{path}"
    if request.query_string:
        target_url += f"?{request.query_string.decode('utf-8')}"

    headers = {key: value for key, value in request.headers if key.lower() not in ['host', 'connection', 'content-length', 'accept-encoding']}

    try:
        resp = requests.request(
            method=request.method,
            url=target_url,
            headers=headers,
            data=request.get_data(),
            cookies=request.cookies,
            allow_redirects=False,
            timeout=30
        )

        excluded_headers = ['content-encoding', 'content-length', 'transfer-encoding', 'connection']
        response_headers = [(name, value) for name, value in resp.raw.headers.items() if name.lower() not in excluded_headers]

        return Response(resp.content, resp.status_code, response_headers)

    except requests.exceptions.RequestException as e:
        print(f"Error forwarding request to {target_url}: {e}")
        return Response(f"Proxy Error: Could not reach target server or invalid response: {e}", status=502)
    except Exception as e:
        print(f"An unexpected error occurred: {e}")
        return Response(f"Internal Proxy Error: {e}", status=500)

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=LISTEN_PORT, debug=True)
```
