# Написание кода интерфейса и документации с помощью больших языковых моделей

На предыдущих уроках мы научились использовать инструменты, такие как Figma, для создания дизайна пользовательского интерфейса, использовать AI для быстрого создания статических фронтенд-страниц и использовать Supabase для построения базы данных и реализации начальной аутентификации пользователей. Теперь перед нами встает естественный вопрос: когда мы нажимаем на динамичные кнопки на фронтенд-странице, как они незаметно сохраняют данные в Supabase? Когда нам нужно выполнить более сложную бизнес-логику (такую как параллельные платежи, запланированные уведомления, обработка конфиденциальных данных), безопасно ли позволять фронтенду напрямую подключаться к базе данных?

Это приводит нас к критически важной части современной веб-архитектуры разработки — **бэкэнд API интерфейсу**.

По сравнению с прошлым, когда нужно было вручную писать сотни или тысячи строк кода маршрутов, контроллеров и логики валидации параметров, сегодня мы можем полностью использовать мощные возможности больших языковых моделей для генерации кода, позволяя AI писать сложный базовый код. В этом уроке мы выйдем из порочного круга "AI пишет пусто и обобщенно" и, опираясь на реальные бизнес-сценарии, покажем вам, как использовать высокое качество промптов для направления больших языковых моделей в написание надежного Node.js бэкэнд-интерфейса, соответствующего отраслевым стандартам, и автоматически генерировать документацию интерфейса и тестовые сценарии.

# 1. Почему нам нужны API интерфейсы?

В традиционном понимании фронтенд — это "видимая часть", а база данных — это "хранилище для сохранения данных". Но между ними отсутствует диспетчер. Если вы представите всё приложение как ресторан:
- **Фронтенд (клиент)** — это меню ресторана и стол для заказов, где клиенты просматривают блюда и выражают свои потребности.
- **База данных (Supabase и т.д.)** — это задняя кухня и хранилище ресторана, где хранятся все ингредиенты и счета.
- **Бэкэнд API интерфейс** — это официант ресторана. Клиенты не могут прямо бежать в заднюю кухню брать ингредиенты (это не только создает беспорядок, но и вызывает проблемы с безопасностью), вместо этого они должны сообщить серверу свои "потребности в заказе" (HTTP Request). После проверки (валидация параметров, проверка разрешений), официант идет в заднюю кухню, получает необходимое содержимое и возвращает "готовое блюдо" (HTTP Response, обычно в формате JSON данных) клиенту.

Через API интерфейс мы реализуем четкое **разделение фронтенда и бэкэнда**: фронтенд сосредотачивается только на том, как отображать страницы, бэкэнд сосредотачивается на бизнес-логике, обработке данных и безопасности.

# 2. Дизайн архитектуры проекта и инициализация

Четко структурированный каркас проекта является предварительным условием для того, чтобы большие языковые модели писали хороший код. Перед тем как просить AI писать код, мы сами должны иметь ясное представление об инженерной структуре.

## 2.1 Обычная структура API проекта
Даже если вы используете большие языковые модели для генерации кода, вы никогда не должны помещать весь код в один файл `server.js`. Обычно хорошо поддерживаемая архитектура Node.js бэкэнда выглядит так:

```text
my-api-project/
├── .env                  # Чувствительные переменные окружения (например, API ключи, строки подключения БД)
├── server.js             # Точка входа проекта (запуск сервера, регистрация глобального middleware)
├── package.json          # Файл управления зависимостями
├── src/
│   ├── routes/           # Слой маршрутизации: определение путей URL и методов запроса
│   ├── controllers/      # Слой контроллеров: обработка параметров бизнес-запроса, вызов сервисов и возврат ответов
│   ├── services/         # Слой сервисов: инкапсуляция взаимодействия с БД и основной бизнес-логики
│   └── middlewares/      # Middleware: аутентификация входа, глобальный перехват ошибок
└── docs/                 # Каталог хранения документации API
```

## 2.2 Завершение инициализации проекта с помощью AI
Вместо того чтобы вручную запускать `npm init` и устанавливать зависимости одну за другой, почему бы не передать указанные выше стандарты большой языковой модели в виде промпта:

> **Пример промпта для большой языковой модели:**
> "Помоги мне построить Node.js бэкэнд проект, который может подключаться к базе данных Supabase, с четкой структурой для удобства будущего обслуживания."

После запуска кода, возвращаемого AI, вы получите бэкэнд приложение уровня предприятия на `localhost:3000`.

# 3. Основная практика: разработка интерфейса с помощью больших языковых моделей

Это самая важная часть этого урока. Код, генерируемый большими языковыми моделями, часто имеет "логические дыры" или "поверхностные недостатки", причина в том, что разработчик предоставил недостаточный контекст. **Большим языковым моделям не страшны сложные требования, их страшат неясные требования.**

Возьмите для примера интерфейс добавления таблицы `menu_items` (меню) из [раздела базы данных](https://github.com/datawhalechina/easy-vibe/blob/main/docs/zh-cn/stage-2/backend/database-supabase/index.md) и посмотрите, как написать высокое качество промпта.

## 3.1 Предоставление большой языковой модели полного контекста
Перед тем как просить AI писать интерфейс, вы должны предоставить **определение полей базы данных (Schema)** и **конкретные ограничения**.

> **Шаблон высокого качества промпта:**
> "Напиши мне интерфейс для добавления новое позиции в меню. Позиция меню содержит название продукта, цену, категорию (гамбургеры, закуски, напитки), доступна ли для продажи. Название и цена обязательны, цена не может быть отрицательной. Когда пользователь вводит неправильные данные, показывай сообщение об ошибке."

## 3.2 Проверка кода, генерируемого большой языковой моделью
Код, генерируемый большой языковой моделью, обычно четко разделяет ответственность, как показано ниже:

```javascript
// services/menuService.js
const { createClient } = require('@supabase/supabase-js');
const supabase = createClient(process.env.SUPABASE_URL, process.env.SUPABASE_KEY);

exports.createMenuItem = async (menuData) => {
    // Вызов Supabase SDK для вставки данных в таблицу
    const { data, error } = await supabase
        .from('menu_items')
        .insert([menuData])
        .select();

    if (error) throw new Error(`Ошибка вставки в БД: ${error.message}`);
    return data[0];
};
```

Вы видите, что код, генерируемый таким способом, не только имеет разумную структуру, но и учитывает инициализацию Supabase, обработку ошибок и обработку исключений, что совершенно отличается от беспорядочного кода "спагетти" (Spaghetti Code), полученного простым требованием "напиши интерфейс для добавления".

# 4. Освобождение рук: автоматическое создание документации интерфейса

Для команды разработчиков API без документации — это черный ящик. Фронтенд-разработчик не может угадать, какие параметры вам нужно передать, и не может предугадать, какую структуру вы вернете. Наиболее универсальный стандарт описания API в отрасли — это **OpenAPI (ранее также называемый Swagger)**.

В прошлом написание вручную документации Swagger в формате YAML или JSON было крайне болезненным и легко приводило к ошибкам. Теперь это стало областью, в которой преуспевают большие языковые модели.

Вы можете напрямую выбрать только что написанный код `routes` и `controllers` и передать его большой языковой модели:

> **Промпт для создания документации:**
> "Помоги мне создать документацию интерфейса на основе кода выше, четко объясни, что означает каждый параметр, какие данные возвращаются, чтобы было удобно моим коллегам-фронтенд-разработчикам интегрировать."

В этом процессе вы даже можете попросить AI заполнить описания полей (Description) и примеры данных (Mock data) (например, `price_cents: 1200` означает 12 долларов), значительно снизив затраты на общение.

# 5. Защита и обеспечение: генерация тестов и Postman наборов

Код написан, документация готова, осталось последний шаг: убедиться, что код действительно работает.

## 5.1 Генерация Postman / Apifox конфигурации
При разработке интерфейсов мы обычно используем такие визуальные инструменты, как Postman, для имитации отправки HTTP-запросов фронтенд-приложением. Если не использовать большие языковые модели, вам нужно вручную ввести URL, добавить Headers (заголовки запроса) один за другим и собрать JSON тело запроса.

Вам просто нужно отправить инструкцию AI:
> "Помоги мне преобразовать эту документацию интерфейса в формат, который может импортировать Postman, включая примеры как обычных, так и ошибочных запросов."

После получения JSON текста сохраните его как `menu_api.json` и перетащите в Postman, вы мгновенно получите набор готовых к использованию тестовых панелей.

## 5.2 Написание автоматизированных единичных тестов
Если вы стремитесь к более строгому инженерному качеству, вы можете попросить большую языковую модель помочь вам написать единичные тесты (Unit Tests) с использованием тестовых фреймворков, таких как `Jest`, для тестирования граничных случаев основной бизнес-логики (например, проверяет ли слой базы данных, что цена не может быть отрицательной).

# 6. Лучшие практики, которые необходимо знать для бэкэнд-интерфейсов

Даже с помощью AI, как "хранитель" всей системы, вам все еще нужно понимать и проверять следующие основные принципы:

1. **Именование путей в соответствии со спецификацией RESTful**:
   - Хороший дизайн: `GET /api/users` (получить список пользователей), `POST /api/users` (создать пользователя). URL должен представлять "ресурс" в именительном падеже.
   - Неправильный дизайн: `POST /api/getUser` или `POST /api/createUser`. Глаголы должны быть представлены HTTP методом (GET/POST/PUT/DELETE).
2. **Стандартные HTTP коды статуса**:
   - 200/201: Запрос успешен / ресурс создан успешно.
   - 400: Bad Request, фронтенд передал неправильный формат параметров или отсутствуют обязательные поля.
   - 401/403: Unauthorized / Forbidden, пользователь не вошел или не имеет разрешения на операцию.
   - 404: NotFound, ресурс не существует.
   - 500: Server Error, код бэкэнда содержит ошибку или база данных не работает, в любом случае старайтесь избежать прямого раскрытия трассировки ошибок фронтенд-части (это представляет риск безопасности).
3. **Никогда не доверяйте вводу пользователя**: вход фронтенда может быть поддельным, все основные проверки параметров должны быть выполнены еще раз на бэкэнд-интерфейсе.
