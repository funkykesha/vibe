## Контекст

`app.py` - небольшое rumps-приложение в menu bar. Оно показывает список жестко заданных LaunchAgent label и дает команды перезапуска через `launchctl`. Сейчас для добавления нового сервиса пользователь должен вручную создать plist в `~/Library/LaunchAgents`, выдержать соглашения по именам и отдельно создать директории логов.

Новый сценарий остается локальным: пункт меню открывает одно окно формы, приложение валидирует поля, пишет plist для текущего пользователя и сообщает результат. XML нужно генерировать через Python API для plist, а не собирать строками.

## Цели / Не цели

**Цели:**

- Добавить пункт меню "Добавить конфиг" или эквивалентный.
- Открывать одно окно редактора с четырьмя полями: `name`, `command`, `path-to-start` и опциональный `WorkingDirectory`.
- Дать пользователю кнопки "Отмена" и "Применить" в этом окне.
- Создать `~/Library/LaunchAgents/com.agaibadulin.<name>.plist`.
- Сформировать Label как `com.agaibadulin.<name>`.
- Использовать пути логов `~/Library/Logs/<name>/stdout.log` и `~/Library/Logs/<name>/error.log`.
- Создать директорию логов, если ее нет.
- Валидировать обязательные поля и показывать ошибки без частично созданных конфигов.

**Не цели:**

- Автоматически загружать, выгружать, bootstrap-ить или запускать новый LaunchAgent.
- Редактировать или удалять существующие LaunchAgent plist.
- Заменять текущий жестко заданный список сервисов динамическим discovery.
- Поддерживать системные LaunchDaemons или привилегированные директории записи.

## Решения

- Использовать AppKit-окно формы поверх rumps, а не цепочку `rumps.Window`.
  - Причина: нужно одно окно с несколькими полями и явной кнопкой "Применить"; rumps удобен для menu bar и простых single-input dialogs, но не для полноценной формы.
  - Рассмотренная альтернатива: четыре последовательных rumps-диалога. Отклонено, потому что пользователь выбрал вариант Б - один редактор с полями.

- Использовать `plistlib.dump` для записи plist.
  - Причина: это исключает ошибки XML-экранирования и создает нативный macOS plist.
  - Рассмотренная альтернатива: строковый XML-шаблон. Отклонено, потому что пользовательский ввод может содержать XML-спецсимволы.

- После валидации использовать `name` как точный суффикс сервиса для Label, имени файла и директории логов.
  - Причина: все производные пути остаются предсказуемыми.
  - Рассмотренная альтернатива: принимать произвольный label. Отклонено, потому что имя файла и директория логов требуют безопасный стабильный идентификатор.

- Ограничить `name` простым безопасным идентификатором: буквы, цифры, underscore и hyphen.
  - Причина: это предотвращает path traversal, неоднозначные label и случайную запись вне нужных директорий.
  - Рассмотренная альтернатива: разрешить любые имена с escaping. Отклонено, потому что LaunchAgent label и имена файлов должны оставаться читаемыми и предсказуемыми.

- Считать `command` и `path-to-start` двумя элементами `ProgramArguments`.
  - Причина: это напрямую соответствует запрошенной форме plist.
  - Рассмотренная альтернатива: парсить shell-команду в много аргументов. Отклонено как отдельная функция с edge cases вокруг кавычек и escaping.

- Добавлять `WorkingDirectory` только если опциональное поле заполнено.
  - Причина: это соответствует запрошенному поведению.
  - Рассмотренная альтернатива: выводить working directory из `path-to-start`. Отклонено, потому что поле задано явно, а аргумент запуска не обязан быть путем к файлу.

## Риски / Компромиссы

- Целевой plist уже существует -> показать ошибку и попросить выбрать другое имя или вручную удалить старый plist.
- Команда или путь запуска некорректны -> plist может быть создан, но LaunchAgent упадет при запуске; валидация гарантирует форму конфига, не работоспособность исполняемого файла.
- Не удалось создать директорию логов -> прервать создание plist и показать filesystem-ошибку.
- Текущее меню все еще использует жестко заданные label -> созданный конфиг может не появиться в списке перезапуска, пока не будет добавлено динамическое discovery.

## План миграции

Миграция не нужна. Функция добавляет пункт меню и пишет новые пользовательские LaunchAgent-файлы только по явному действию пользователя. Rollback - удалить новый code path; уже созданные plist остаются пользовательскими файлами и могут быть удалены вручную.
